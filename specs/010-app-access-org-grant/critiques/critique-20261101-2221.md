# Critique Report: 应用访问按组织架构授权

**Date**: 2026-11-01
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

方向与边界都对：用「应用 × 部门（含子部门）」这一条关系替代 003 的一次性快照补员，是当前数据模型下最省事的解法；不物化成员、按物化路径实时判定、撤销不触碰手动成员与角色绑定、部门删除加引用校验，这几条都与既有实现（`organizations.path`、`client_members.is_admin`、002 的写事务语义）咬合得很紧。`OrgGrantMatchSQL` 单一判定实现、把撤销影响人数预置进列表响应、明确拒绝"跨工程抽公共组件"，也都是有意识的减法。

但有一个**定位级**问题必须在写代码前拍板：spec 通篇把组织授权称作"访问权限"（FR-011 "股东获得该应用的访问权限"、FR-007 "37 人将不再可见"），而系统现状是——**OIDC 授权端点根本不校验成员关系**（`internal/oidc/claims.go:55` 的 `IsClientMember` 只用于 userinfo 计算字段，`internal/oidc/storage.go:76` 只校验账号 `status`），且移除成员从不吊销既有会话与令牌（`internal/store/app_auth_store.go:256-281`）。也就是说今天"不是成员"的人只要知道 SP 地址，照样能完成 SSO 并拿到令牌。若不自证这一点，本特性会被当成一个"能拦人"的访问控制上线，实际只是个门户列表过滤器——这是安全预期落差，不是实现瑕疵。

此外还有两处工程硬伤（事务外校验部门存在 → 可写入悬空 `org_id`；撤销响应的 `impactUsers` 语义自相矛盾），以及 11 条改进建议与 3 个需要产品/安全侧回答的问题。

## Product Lens Findings 🎯

### Problem Validation

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| P1 | 💡 | 痛点真实但**只写了"现状低效"，没写"为什么现在"**：003 上线后每个应用都靠快照补员，一次组织调整要人工重跑几十个应用——这是可量化的运维成本，spec 只在 Why this priority 里一句带过。内部项目可以接受，但下一个人（或下一轮评审）无法判断"能不能再拖一个季度"。 | 在 `## Input` 或 `## Assumptions` 补一行动因与规模：例如"003 上线后 N 个应用、月均 M 次补员操作；组织调整平均 T+2 才补齐"。不新增需求，只为可追溯。 |

### User Value Assessment

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| P2 | 💡 | **缺少"存量快照 → 组织授权"的迁移引导，管理员会被迫逐个应用重配。** 003 已经产生了一批"按部门一次性加入"的成员，它们在 spec 里被定义为"历史手动成员、不回滚"（FR-026）——正确，但管理员看到的是"某个应用下有 120 个成员，其实全来自同一个部门"，却没有工具把这 120 行折成 1 条组织授权。迁移成本被静默转嫁给了最该被减轻的人。 | 在成员页加一条**只读提示**（不新增写能力）：当某部门快照成员数 ≥ 阈值且该部门尚未被授权时，提示"研发部有 118 名成员来自历史批量加入，可改为组织授权以避免继续补员"。若判定为范围外，至少在 quickstart/部署文档写明"存量应用需逐个应用配置组织授权"的操作清单。 |
| P3 | 🎯 | **"访问权限"的措辞与实际生效范围不符（详见 X1）。** FR-011 只说"门户『我的应用』返回…"，但 User Story 1 与 SC-003 的表述是"获得访问权限""不再可见"；管理员据此会认为撤销授权即"这人进不去了"。实际：只要会话还在、SP 地址还被知道，用户仍可完成授权码流程。**这是本特性最容易被误解为安全控制的地方，且误解方向是"高估安全性"。** | 二选一并写进 spec：**①（推荐本期）** 明确降级为"门户可见性与入口收敛"，在 FR-011 与 Key Entities 里把"访问权"改为"门户可见性"，并在文档/页面文案写明"组织授权不阻断直接访问 SP 的 SSO 流程（与既有成员制一致）"；**②（若必须真拦）** 新增 FR：`/oauth2/authorize` 在签发前校验「成员 ∨ 组织授权覆盖 ∨ 应用启用 ∨ 账号启用」，未命中返回 `access_denied`，并定义撤销时是否吊销该用户在该应用的有效令牌。**两者工作量差一个数量级，不能含糊。** |

### Alternative Approaches

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| P4 | 💡 | **没有"跨应用复用组织授权"的路径。** 现实中同一套部门往往要开通同一批应用（研发部 → 全部研发工具）。本特性要求逐应用操作，50 个应用 = 50 次重复劳动，产品价值被稀释一半。 | 本期不做（保持范围），但在 spec `## Assumptions` 明确"暂不提供批量/跨应用复制"，并把"复制到其他应用"记入 v2 候选；接口形态上预留（`POST .../org-grants` 的 `grants[]` 已可复用，不需改契约）。 |
| P5 | 💡 | 撤销后**受影响用户没有任何感知**（无站内信、无门户提示），他们下一次点应用要么被 SP 报 401、要么直接进不去；支持成本会从"补员"转移到"为什么我进不去了"。 | 见 Q1：若不做通知，至少在审计 `detail.impactUsers` 之外提供"影响名单可查"（列表接口已可算，不必新增存储）；若要做通知，走既有 `notification` 通道，属独立特性。 |

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 💡 | **单一判定片段是正确选择，但 plan 没把"等价性"变成可执行门禁。** `OrgGrantMatchSQL` 被 6 处复用，一旦某处少写一个括号或缺 `include_sub` 分支，表现是"某人莫名看不到应用"，测试很难兜住。research R3 只写了"由 integration 测试断言等价"，但 tasks 阶段很可能只落 2–3 个 happy path。 | 在 plan/tasks 里固定一条用例：**同一组 fixture 下，`/me/apps` 的可见集合 == 授权列表的覆盖人数之和（去重后）**，两侧走不同 SQL 却必须收敛；再加一条"`include_sub=0` 时子孙部门不被计入"。把这两条写成必须存在的测试名，避免实现期被简化掉。 |
| E2 | 🎯 | **部门存在性校验在事务外，可写入悬空 `org_id`。** plan GT-2 写的是"service 写前校验（复用 `GetOrganization`）"——这是**先查后写**。部门在"查完"与"插入"之间被删除（管理员并发操作，或 002 的删除保护此时尚未看到本授权）→ `client_org_grants` 留下指向已删部门的行，覆盖人数变 0 而无人察觉。项目对同类问题已有明确做法：`users.dept_id` 写入时在短事务内 `LockOrganization`（AGENTS §4.1 的行为修正段），以及对 `organizations` 写操作加全表锁。 | 把校验搬进写事务：`store.Transaction` 内先 `LockOrganization(orgID)`（不存在即 `ErrAppDeptNotFound`），再读写授权、再 `HasOrgGrants` 计数（上限判定也在同一事务内，顺带解决 E4）。与 002 的并发语义保持一致。 |
| E3 | 💡 | `POST .../org-grants` 的"整批一个事务"是对的，但契约里 `added/updated/unchanged` 三态与 `INSERT ... ON DUPLICATE KEY UPDATE` 天然打架：若 `updated_at` 无条件刷新，MySQL 的 `RowsAffected` 对已存在行恒为 2（changed），`unchanged` 永远是 0，前端提示永远说"已更新 1 条"。 | 契约里明确：**先按 `(client_id, org_id)` 读出既有 `include_sub`，再分流为 insert / update / no-op**（或 `UPDATE ... WHERE include_sub <> ?` + 检查 `RowsAffected`），不要依赖 `ON DUPLICATE KEY` 的影响行数做三态。 |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E4 | 💡 | 上限 500 的判定如果没有行锁，并发两次提交可同时读到 499 → 501 条，属"软上限"。这类缺陷上线后极难复现，但也无害。 | 既然 E2 已要求进事务，顺手在同一事务内 `COUNT` 即可（成本为零）；如判定为可接受，在契约里写明"上限为软限制，允许并发少量超出"，避免后续被当 bug 报。 |
| E5 | 🎯 | **GT-3 的 `impactUsers` 自相矛盾。** 契约原文：「撤销后**仅因这些授权而可见**的账号数」——撤销后它们恰恰不再可见，按字面实现会恒返回 0，正好掉进"前端提示已撤销 0 人受影响"的坑。spec FR-007 要求的是"撤销**将**导致多少人不再可见"，是**删除前**的预测量。 | 契约改为：「`impactUsers` = 在**同一事务内、删除之前**计算的『命中待撤销授权 ∧ 非手动成员 ∧ 未被其它保留授权命中』去重人数」，并补一句"若事务内计数失败则整次撤销失败"，防止"删了但提示不知道影响多少人"。 |

### Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | 🎯 | **撤销组织授权后，已签发的令牌与既有 SSO 会话照旧有效**（`RemoveMembers` 也只删成员与角色绑定，不吊销令牌；`sessions` 是用户级、与应用无关）。若选 X1 的方案②，必须同时定义吊销范围，否则"撤销"只影响下一次授权码流程，对已登录用户完全无效；若选方案①，则必须在文档里写明这一事实，防止运维把它当离职处置手段。 | 与 X1 合并决策：方案①→ 在 `docs/deployment.md` 与页面文案写明"撤销不终止已生效的会话/令牌，离职处置仍需停用账号（会即时失效）"；方案②→ 新增吊销：按 `access_tokens(client_id, sub)` + `refresh_tokens` 家族吊销，并在撤销响应里回传 `revokedSessions`。**本期建议方案①，但必须写清。** |
| E7 | 💡 | 门户 appAdmin 校验已有成熟语义（403 同文案、不泄露存在性），但新端点容易漏挂 `appAdminGroup` 而落到 `authed` 组——那样任何登录用户都能读某应用的组织授权列表（含部门名与人数），是信息泄露。 | 在 plan 的契约章节显式写"三条门户路由 MUST 注册在 `appAdminGroup`"，并在 `router_test.go` 加一条断言：未授权用户请求 `GET /me/apps/:id/org-grants` 返回 403（现有测试已有类似形态可复用）。 |

### Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E8 | 💡 | **`o.path LIKE CONCAT(go.path,'%')` 的模式来自列值，MySQL 无法用 `organizations.path` 索引**，覆盖人数聚合会退化为"每条授权扫一遍 organizations"。表小（<1e3 行）时无感，但这条 SQL 是整个特性最热的查询，值得留痕。 | 在 plan/quickstart 增加一步 `EXPLAIN` 与 fixtures 计时（20 条授权 / 2000 人子树），把结果写进 PR；若实测超 SC-005，备选改写是"Go 侧解析 `dept.path` 得祖先 ID 集合 → `g.org_id IN (...)`"，索引友好且判定仍唯一。**不改契约，只留升级路径。** |
| E9 | 💡 | `visibleTotal` 是**全表聚合**（扫 `users` 一次 + 两次 EXISTS），而成员页每次翻页、每次筛选都会重算。成员页是管理员的高频页面，翻 10 页就是 10 次全扫。 | 只在 `page=1`（或首次加载）计算 `visibleTotal`，翻页时回传上次值；或拆成 `GET .../access-summary` 单独拉一次。二选一写进契约，避免实现期各写各的。 |

## Cross-Lens Insights 🔗

| ID | Finding | Product Impact | Engineering Impact | Suggestion |
|----|---------|---------------|-------------------|------------|
