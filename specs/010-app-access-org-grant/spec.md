# Feature Specification: 应用访问按组织架构授权

**Feature Branch**: `010-app-access-org-grant`

**Created**: 2026-11-01

**Status**: Draft

**Input**: User description: "应用访问支持按组织架构授权：管理员为应用授予某个部门（可选择是否包含子部门）后，该部门下的员工自动获得这个应用的访问权限，门户'我的应用'自动出现、可以直接单点登录；组织再变动（新人入职、调岗、离职停用、部门合并）时权限自动跟随，不再需要管理员一次性'按部门批量加入成员'再人工补员。admin 端与门户应用管理员端行为一致，组织授权的增删要留审计，能看出谁授权了哪个部门、影响多少人。"

## Clarifications

### Session 2026-11-01

- Q: 既有的「按部门批量加入成员」入口是否与新「按组织授权」并存？ → A: 不并存。用户可见入口由组织授权取代（FR-027），避免两套部门级授权入口并行、管理员无法判断哪套生效；存量快照成员保留为手动成员且不回滚（FR-026）；若既有接口需保留兼容期，须标注弃用并通过单独提交下线。
- Q: 把组织树根节点授予应用，是否等于重新引入「全员可见/公开应用」例外开关？ → A: 不等于。根节点是组织树中的普通节点，允许授予；但因一次授权可能放开全部在职员工，保存 MUST 二次确认并显示将被覆盖的在职员工总数（FR-006）。这属于「显式选择组织节点」的自然结果，不构成例外开关。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员按组织授权，员工无需被逐个添加即可使用应用 (Priority: P1)

平台管理员在应用的成员管理里，不再逐个挑人，而是直接选一个部门（默认包含其下级部门）授予访问权限。授权保存后，该部门下所有在职员工登录门户就能在"我的应用"里看到这个应用并直接进入，管理员不需要再做任何"把人加进来"的动作。

**Why this priority**：这是本特性的全部价值所在。现状是按部门"批量加成员"的一次性快照——把当时部门里的人写进成员表，之后部门里再来人就看不到应用，只能靠人工补员；按组织授权直接消灭这条人工补员链路，是本特性的核心，必须先成立。

**Independent Test**：新建测试应用 C，只做一次"授予部门『研发部（含子部门）』"的操作，然后用研发部及其下级部门的员工账号登录门户，确认能看到并用 C；再用不在该部门树内的员工账号登录，确认看不到 C。全程不添加任何单个成员。

**Acceptance Scenarios**：

1. **Given** 应用 C 尚无任何成员与组织授权，**When** 管理员选择部门"研发部"并勾选"包含子部门"后保存，**Then** 授权列表新增一条记录，显示部门名、是否含子部门、当前覆盖人数，且无需再执行任何其他操作。
2. **Given** 应用 C 已授权"研发部（含子部门）"，**When** 研发部下级"平台组"的员工登录门户打开"我的应用"，**Then** C 出现在列表中，点击可直接完成单点登录并落在应用页面。
3. **Given** 应用 C 已授权"研发部（不含子部门）"，**When** 研发部下级"平台组"的员工登录门户，**Then** 看不到 C；研发部本级的员工则能看到 C。
4. **Given** 同一部门被重复提交授权，**When** 管理员再次保存同一部门，**Then** 不新增重复记录、不报错，覆盖人数不变。
5. **Given** 管理员把应用 C 的组织授权从"研发部（含子部门）"改为"市场部"，**When** 保存成功，**Then** 研发部树内不再可见 C，市场部树内可见 C，两端（admin 与门户）看到的结果一致。

### User Story 2 - 组织变动后访问权限自动跟随 (Priority: P1)

员工的部门归属发生变化（新人入职、调岗、部门合并、离职停用）时，其在各个应用上的可见性自动跟着变：新进部门的人立刻能看到该部门被授权的应用，调离的人立刻看不到，不需要管理员跑一遍补员。

**Why this priority**：只做一次性授权而不做自动跟随，等价于把"批量加成员"换个地方重做一遍，问题没有解决；同时组织变动是日常高频事件，它决定这套机制是否真正省人工。

**Independent Test**：应用 C 只授权"研发部（含子部门）"。把一名市场部员工调入研发部下的"平台组"，该员工刷新门户即可看到 C；再把他调回市场部，刷新后 C 消失。全程不做任何应用侧操作。

**Acceptance Scenarios**：

1. **Given** 员工 E 属于市场部、应用 C 授权了"研发部（含子部门）"，**When** 管理员把 E 调岗到研发部下的平台组，**Then** E 下次打开"我的应用"即可看到 C，无需授权侧操作。
2. **Given** 员工 E 因所在部门被授而能看到 C，**When** 管理员把 E 调岗到未被授权的部门，**Then** E 下次打开"我的应用"不再看到 C（除非其在 C 中另有手动成员身份或其他组织授权覆盖）。
3. **Given** 新员工入职并分配到已授权部门，**When** 该员工首次登录门户，**Then** 直接能看到该部门被授权的全部应用。
4. **Given** 员工账号被停用（离职），**When** 该员工尝试登录或刷新门户，**Then** 不再能看到任何应用，即使其部门仍被授权。
5. **Given** 部门"平台组"被合并到"架构组"（原部门删除、人员迁入新部门），**When** 管理员把授权对象调整为"架构组"，**Then** 原平台组的人员按新部门归属继续可见，中途不出现"集体失去权限且无人察觉"的状态（调整前的覆盖人数与调整后的覆盖人数在页面上均可核对）。

### User Story 3 - 授权来源可见，撤销时结果可预期 (Priority: P2)

管理员打开某个应用的成员页，能一眼看出每个人是怎么获得访问权的：手动加入的、还是因为哪个部门授权（多个来源都列出来）。撤销一条组织授权时，页面先说清楚"其中多少人会因此彻底看不到这个应用"，撤销后手动加入的成员不受影响。

**Why this priority**：组织授权与手动成员并存后，"这个人为啥能看到这个应用"是排障第一名的问题；撤销时的连带影响如果不可预期，管理员会不敢动，机制就退化成摆设。

**Independent Test**：应用 C 同时有 3 名手动成员和 1 条"研发部"授权（部门内 10 人，其中 2 人也是手动成员）。撤销该授权后，那 2 名手动成员仍在成员列表且仍可见 C，另外 8 人从门户消失；撤销前的确认框显示"8 人将不再可见"。

**Acceptance Scenarios**：

1. **Given** 员工 E 既是 C 的手动成员，又被"研发部"授权覆盖，**When** 查看成员列表，**Then** E 的来源显示为手动 + 研发部（两个来源都列出，不是二选一）。
2. **Given** 一条组织授权当前覆盖 10 人，其中 2 人另有手动成员身份或另一条组织授权覆盖，**When** 管理员点击撤销，**Then** 确认框显示"撤销后 8 人将不再可见"，而不是 10 人。
3. **Given** 管理员确认撤销该授权，**When** 撤销完成，**Then** 手动成员关系、角色绑定、成员加入时间均不改变，仅该条组织授权消失。
4. **Given** 员工 E 仅因组织授权可见 C（无角色），**When** 管理员在授权管理里给 E 授予 C 的应用角色，**Then** E 自动成为 C 的正式成员（来源中新增"手动"），角色对 E 生效。
5. **Given** 一条组织授权覆盖人数为 0（空部门），**When** 管理员查看列表，**Then** 记录仍存在并显示"0 人"，不自动删除。

### User Story 4 - 门户应用管理员具备同等能力 (Priority: P2)

被设为应用管理员的业务同事，在门户的应用管理里也能管理该应用的组织授权（新增、撤销、看覆盖人数），与平台管理员在 admin 端看到的结果完全一致，不必等 IT 代为操作。

**Why this priority**：部门授权属于业务侧的日常动作，若只有平台管理员能做，IT 仍然是瓶颈；006 已经把成员、角色、权限、授权下放到门户应用管理员，本能力需要对齐，避免两端行为分叉。

**Independent Test**：以应用管理员身份登录门户，为应用 C 授权"市场部（含子部门）"，然后在 admin 端用平台管理员账号打开同一应用，确认组织授权列表内容与覆盖人数一致。

**Acceptance Scenarios**：

1. **Given** 用户 U 是应用 C 的应用管理员（非平台管理员），**When** U 在门户为 C 新增一条组织授权，**Then** 操作成功，且 admin 端同一应用立即可见该授权。
2. **Given** 用户 U 是应用 C 的应用管理员但不是平台管理员，**When** U 尝试对另一应用 D 做组织授权，**Then** 请求被拒绝（原因不泄露 D 是否存在）。
3. **Given** 用户 U 既不是 C 的成员也不是 C 的应用管理员，**When** U 请求 C 的组织授权列表，**Then** 请求被拒绝。
4. **Given** 应用 C 已被停用，**When** U 打开 C 的组织授权页，**Then** 页面可见但与其它信息一样标注停用，且授权变更照常保存、对门户可见性暂不生效（停用期间全员不可见）。

---

### User Story 5 - 组织授权变更可追溯 (Priority: P3)

安全与运维在审计日志里能看到"谁在什么时候为哪个应用授权了哪个部门、是否含子部门、影响多少人"，以及撤销记录，用于回答"这个部门的员工为什么能进这个系统"。

**Why this priority**：组织授权是扩大访问面的动作，一次授权可能一次性放开几百人；没有审计就无法在事后追责与复盘。它不阻塞主流程，但属于上线前必须闭环的安全要求。

**Independent Test**：对应用 C 做一次新增授权与一次撤销授权，在审计页分别按这两类事件筛选，各出现 1 条记录，字段含应用、部门名（含层级路径）、是否含子部门、操作者、影响人数与时间。

**Acceptance Scenarios**：

1. **Given** 管理员为 C 新增组织授权"研发部（含子部门）"覆盖 42 人，**When** 查询审计日志，**Then** 出现 1 条新增事件，含上述全部字段，且时间与操作者正确。
2. **Given** 管理员撤销该授权，**When** 查询审计日志，**Then** 出现 1 条撤销事件，影响人数为 42（或撤销时刻的实际覆盖人数）。
3. **Given** 管理员在审计页按事件类型筛选"组织授权"，**When** 选择其中一类，**Then** 只返回该类事件，分页与既有事件一致。
4. **Given** 一次保存中既新增又撤销了授权（多选提交），**When** 查询审计日志，**Then** 两类事件各自独立记录，不合并成一条。

---

### Edge Cases

- 应用被停用：组织授权记录保留、页面可见并标注停用，但门户对所有人不可见；重新启用后立即恢复（不要求重新授权）。
- 部门被删除：删除前若仍被任何应用授权，删除 MUST 被拒绝并提示被哪些应用引用；管理员先撤销授权再删除部门，避免出现指向不存在部门的悬空记录。
- 授予根组织（组织树的顶层节点）：等价于对该组织下全部在职员工放开，页面 MUST 二次确认并显示"将覆盖全部 N 名在职员工"；这是显式选择组织节点的结果，不是"公开应用/全员可见"开关。
- 同一员工被多个来源覆盖（手动 + 多个部门授权）：只要仍有一个来源成立即保持可见；撤销其中一个来源不影响其余。
- 已停用账号（`status≠1`）：无论被多少组织授权覆盖，门户均不可见，且不计入"覆盖人数"的有效值（覆盖人数口径见 FR-005）。
- 应用的组织授权数量很多、部门树很深：授权列表与覆盖人数在千级员工规模下仍能正常加载，不出现超时或空白页（见 SC-005）。
- 组织树读取失败：页面 MUST 明确提示"组织架构加载失败，请重试"，MUST NOT 静默显示空树（否则管理员会误以为部门不存在）。
- 授权提交瞬间目标部门已被删除：整次请求失败并提示"部门不存在"，不写入部分记录。
- 应用暂无任何成员与组织授权：门户对所有人不可见（延续成员制语义），成员页以空态 + "添加组织授权"引导。
- 存量应用此前用"按部门批量加入"拉进来的成员：保持成员身份不变，来源显示为手动，不做回滚。
- **撤销授权后已登录的用户**：其门户列表下一次刷新即不再显示该应用，但已生效的 SSO 会话与已签发的令牌**不会**被回收（本特性不改变 OIDC 行为，见 FR-029）；因此撤销不得被当作离职处置手段，页面与文档必须写明这一点。
- 组织授权**不是访问控制**：知道接入方地址的人即使不在授权范围，仍能走完标准授权码流程（与既有成员制一致）。这是本特性的既定边界，不是缺陷；因此不存在"未授权用户被 authorize 拒绝"这一分支。
- 组织授权卡片自身加载失败（列表或覆盖人数查询失败）：该卡片 MUST 显示可重试错误，成员列表 MUST 照常展示；`visibleTotal` 取不到时显示"—"，不得显示 0（否则会被读成"没人能看见"）。

## Requirements *(mandatory)*

### Functional Requirements

**授权对象与维护**

- **FR-001**: 应用成员管理 MUST 提供「组织授权」能力：列出当前应用的全部组织授权（部门名、层级路径、是否含子部门、当前覆盖人数、授权时间、授权人），并支持新增与撤销。
- **FR-002**: 新增组织授权 MUST 允许一次选择多个部门；每个部门 MUST 可单独设置"是否包含子部门"，默认包含子部门。
- **FR-003**: 同一应用对同一部门 MUST 只保留一条授权；重复提交 MUST 幂等（不报错、不产生重复记录），如"是否含子部门"与已有记录不同则 MUST 更新该设置并留下审计。
- **FR-004**: 授权列表 MUST 显示每条授权当前覆盖的人数；覆盖人数 MUST 与门户可见性判定使用同一口径，MUST NOT 由两套独立逻辑各算一次。
- **FR-005**: "覆盖人数"口径 MUST 为：满足该授权条件（部门本级，含子部门时为其整棵子树）、账号处于在职启用状态（`status=1`）的**账号数**；界面 MUST 标注该口径（"在职启用账号数"），避免管理员拿它与含停用账号的花名册直接对账而误判漏人。
- **FR-006**: 授予组织树根节点 MUST 二次确认，并在确认框中显示将被覆盖的在职员工总数。
- **FR-007**: 撤销组织授权 MUST 二次确认，并显示"撤销后 X 人将不再可见"（X = 仅因该授权而可见的人数，不含仍有其它来源的成员，也不含停用账号）；同一确认框 MUST 附带显示"另有 N 个停用账号被该授权覆盖（不影响可见性）"，该值 MUST 由同一次计算得出、不额外增加查询。
- **FR-008**: 撤销组织授权 MUST NOT 删除用户、MUST NOT 解除角色绑定、MUST NOT 改变手动成员的加入时间与加入人。
- **FR-009**: 授权的部门 MUST 存在于组织架构中；目标部门不存在时整次请求 MUST 失败并提示"部门不存在"，MUST NOT 写入部分记录。
- **FR-010**: 单个应用的组织授权数量 MUST 有上限（默认 500 条），超出时 MUST 明确拒绝并提示上限。

**门户可见性与边界**

- **FR-011**: 门户「我的应用」MUST 返回同时满足以下条件的应用：① 应用处于启用状态；② 当前账号处于在职启用状态；③ 该用户是应用的手动成员，**或**被至少一条组织授权覆盖。本特性定义的是**门户可见性与入口收敛**，不构成访问控制（边界见 FR-029）。
- **FR-012**: 「被组织授权覆盖」MUST 按用户当前所属部门实时判定：授权含子部门时命中该部门整棵子树内的人员，不含子部门时仅命中该部门本级人员。
- **FR-013**: 用户在组织架构中的部门归属发生变化（含入职分配、调岗、停用）后，其可见性 MUST 在下一次请求时即按新归属计算，MUST NOT 依赖定时任务、后台同步或人工补员；判定 MUST NOT 使用长时缓存。
- **FR-014**: 组织授权 MUST NOT 改变 OIDC 协议端点行为：用户信息接口返回的应用内角色与权限点 MUST 仍按"是否为该应用成员"计算，既有字段含义与类型保持不变。
- **FR-015**: 非成员但被组织授权覆盖的用户，在被授予应用角色时 MUST 自动成为该应用的正式成员（沿用既有"有角色必然是成员"的不变量），页面 MUST 提示已自动加入成员。

**与手动成员的关系**

- **FR-016**: 成员列表 MUST 显示每位成员的访问来源：手动、以及覆盖其的全部组织授权（以部门名展示）；来源超过 2 个时 MUST 折叠为"手动 + N 个组织"，并可展开查看全部。
- **FR-017**: 移除手动成员 MUST 只解除手动成员关系；若该用户仍被组织授权覆盖，撤销后 MUST 继续可见，且页面 MUST 提示"该用户仍可通过 N 个组织授权访问"。
- **FR-018**: 添加成员时，已被组织授权覆盖的用户 MUST NOT 被静默排除，也 MUST NOT 被自动批量加入；候选中 MUST 标记"已可通过组织授权访问"，由管理员显式决定是否加为正式成员。
- **FR-019**: 成员总数 MUST 与"手动成员数 + 组织授权覆盖人数去重后的实际可见人数"口径一致，页面 MUST 能区分展示两者，不出现"成员 3 人但可见 40 人"却无任何说明的状态。

**两端一致与权限**

- **FR-020**: admin 端与门户应用管理员端 MUST 提供同一套组织授权能力（列表、新增、撤销、覆盖人数、二次确认文案），两端查询结果 MUST 一致。
- **FR-021**: admin 端 MUST 仅平台管理员可操作；门户 MUST 仅该应用的应用管理员可操作，判定沿用既有规则（实时查库、不使用缓存），拒绝语义 MUST 与既有应用管理端点统一，不泄露应用是否存在。
- **FR-022**: 组织树数据 MUST 复用既有的组织树来源；加载失败时 MUST 向用户显示可重试的错误提示，MUST NOT 静默降级为空树。

**审计**

- **FR-023**: 新增一条组织授权与撤销一条组织授权 MUST 各写入 1 条独立审计事件（分别对应新增与撤销两类，可被审计页按类型筛选），内容 MUST 包含：操作者、应用、部门名与层级路径、是否含子部门、影响人数、结果与时间。
- **FR-024**: 一次提交涉及多条授权变更时 MUST 按条记录，MUST NOT 合并为单条事件；失败的操作 MUST 记录为失败，MUST NOT 记为成功。
- **FR-025**: 审计事件类型 MUST 登记进项目既有的事件注册表与一致性检查范围，保证"代码有、规范有、文档有"三者不漂移。

**兼容与存量**

- **FR-026**: 存量通过"按部门批量加入"产生的成员记录 MUST 保持不变，来源显示为手动；本特性 MUST NOT 对存量数据做自动迁移或回滚。
- **FR-027**: 面向用户的"按部门批量加入成员"入口 MUST 由"按组织授权"取代；若既有接口需保留兼容期，MUST 标注弃用并通过单独提交下线，本特性 MUST NOT 同时存在两套并行的部门级授权入口而让管理员无法判断哪套生效。
- **FR-028**: 部门删除前的引用校验 MUST 覆盖组织授权（与成员关系的引用校验同等对待）。
- **FR-031**: 当某部门在本应用中的成员数达到提示阈值（默认 20 人）且该部门及其祖先部门均未被组织授权时，成员页 MUST 以只读提示建议改用组织授权（最多展示 3 条、可按条关闭）；本特性 MUST NOT 自动把这些成员转换为组织授权，MUST NOT 因提示而修改任何成员关系。

**边界与降级**

- **FR-029**: 组织授权 MUST NOT 被实现或宣称为访问控制：MUST NOT 阻断接入方（SP）直接发起的标准 SSO 授权流程，MUST NOT 终止已生效的会话或已签发的令牌；离职与越权处置 MUST 以停用账号为准（停用即时失效）。管理页面文案与部署文档 MUST 写明"撤销组织授权不会让已登录用户掉线，也不会阻止其直接访问接入方"。
- **FR-030**: 组织授权卡片（列表或覆盖人数）加载失败时 MUST 显示可重试的错误提示且 MUST NOT 阻塞成员列表展示；可见总人数不可得时 MUST 显示"—"，MUST NOT 以 0 代替。

### Key Entities *(include if feature involves data)*

- **组织授权**：一条「应用 × 部门」的门户可见性许可，属性含是否包含子部门、授权人、授权时间、最近一次设置变更时间。同一应用同一部门至多一条。
- **门户可见性（派生结果）**：某用户的门户「我的应用」是否展示某应用，由「手动成员身份」「其所属部门命中的组织授权」「应用是否启用」「账号是否在职启用」共同决定，不单独存储。它**不是**访问控制：不参与 OIDC 授权判定，也不回收既有会话与令牌（见 FR-029）。
- **应用成员**：应用内的正式成员关系，仍是角色绑定的前置条件，含加入人、加入时间、是否应用管理员。
- **组织节点**：部门树中的节点，含层级路径，是组织授权的授予对象与人员归属判定的依据。
- **审计事件**：组织授权的新增与撤销记录，含上述授权属性与影响人数。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员为应用完成一次"按部门授权"后，该部门员工在门户看到该应用所需的额外人工操作次数为 0（改前需要按部门人数逐个补员或重跑批量加入）。
- **SC-002**: 抽取 20 个组织变动的样例（入职、调岗、停用、子部门迁移、部门合并），变动后员工可见性 100% 与预期一致，且不产生任何应用侧人工操作。
- **SC-003**: 撤销一条组织授权后，仅因该授权可见的员工在下一次刷新门户时 100% 不再看到该应用；仍有其它来源的员工 100% 保持可见（口径只覆盖门户列表与入口，不含既有会话与令牌的回收，见 FR-029）。
- **SC-004**: 上线前后各取两周，成员页「添加成员 / 按部门加入」类写操作次数（以 `app_member_added` 审计事件计数）下降 ≥ 50%；该指标不依赖任何外部工单系统，可直接由审计数据核算。
- **SC-005**: 在"单个部门子树含 2000 名在职员工、该应用已配置 20 条组织授权"的固定数据下，按**服务端 p95（trace 计时）**：保存一次组织授权 ≤ 3 秒，授权列表（含覆盖人数）≤ 2 秒。
- **SC-006**: 审计日志中组织授权的新增与撤销操作 100% 可查到操作者、部门与影响人数，且能按事件类型筛选出全部相关记录。
- **SC-007**: 管理员能在不询问研发的前提下，仅凭成员页信息回答"某员工为什么能看到这个应用"，抽样 10 例 100% 答对。

## Assumptions

- 组织授权只决定"能否看到并使用该应用"，**不直接授予应用内角色与权限点**；角色与权限点仍须显式授予具体成员（授予时自动补成员，见 FR-015）。这样既保持既有"有角色必是成员"的不变量，也避免一次部门授权意外放大权限面。
- 不提供"公开应用 / 全员可见"开关（延续既有约束）；授予根组织是"显式选择组织节点"的自然结果，通过二次确认与人数提示暴露其影响面，不视为例外开关。
- 可见性按请求实时计算，不引入组织授权的物化成员行、定时同步任务或长时缓存；性能以索引与查询优化解决（对应 SC-005）。
- 组织授权沿用既有组织树的部门层级与"是否含子部门"语义，不新增第二套组织维度（如岗位、标签、用户组）。
- 存量"按部门批量加入"的成员记录视为历史手动成员，不追溯来源；不要求把存量成员反向识别为组织授权。
- 组织架构的删除保护、10 级深度限制、成环校验等既有约束不变；本特性只增加"被授权引用"这一条删除前置校验。
- 跨租户场景不在本特性范围内：当前部署为单租户默认值，组织授权不引入按租户隔离的新规则。
- 应用停用期间组织授权保留且不失效，重新启用后立即生效；不要求管理员重新授权。
