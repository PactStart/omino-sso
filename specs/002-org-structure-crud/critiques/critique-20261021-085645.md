# Critique Report: 管理后台组织架构增删改

**Date**: 2026-10-21
**Feature**: [spec.md](../spec.md)
**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

---

## Executive Summary

规格本身质量较高：10 条决策全部落到了可测的 FR/边界用例，契约（3 个端点、4 个错误码、3 个审计事件）与既有统一响应/文档门禁衔接清晰，"不新增迁移、不新增依赖"的保守取舍也站得住。技术上，ID 型物化路径 + 事务内串行化的组合能覆盖四类业务约束，是当前表结构下的合理选择。

但评审发现 4 个必须在实现前修掉的问题：① 用户故事 2 把"移动部门"写成管理员的日常动作，而 FR-017 与管理后台实现只给了新增/重命名/删除三个入口，导致该用户故事在界面上无法完成；② 计划声称"锁按租户过滤、跨租户互不阻塞"，但 `organizations` 表没有 `tenant_id` 索引，`WHERE tenant_id = ? FOR UPDATE` 实际会全表扫描并锁全表；③ 删除部门与"创建/调整用户所属部门"并发时，会产生 `users.dept_id` 悬空（规格的边界用例未覆盖）；④ 新增审计事件在前端无法筛选与显示，因为事件标签表是硬编码的，而计划的文件清单里没有它。四项修复成本都很低，但漏掉任一项都会直接削弱验收结论。

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | **并发方案的事实前提不成立**：plan R2 与 data-model §8 写"锁按 `tenant_id` 过滤，跨租户互不阻塞"，但 `organizations` 只有 `idx_orgs_parent` 与 `idx_orgs_path`，没有 `tenant_id` 索引。`SELECT ... WHERE tenant_id = ? ORDER BY id FOR UPDATE` 会走全表扫描（或 PK 扫描后过滤），InnoDB 对扫描到的行与间隙全部加锁 → 实际是**全局串行化**，任何租户的新增/移动/删除都会互相阻塞。当前单租户下行为正确，但文档结论错误，后续多租户会被误导。 | 二选一并写进 plan/data-model：①（推荐，零迁移）承认"写操作全局串行化"，把锁语句简化为 `SELECT id, parent_id, path FROM organizations ORDER BY id FOR UPDATE`，删除"按租户过滤""跨租户互不阻塞"表述，并在 Complexity Tracking 记录该取舍；② 若确需租户隔离，加 `KEY idx_orgs_tenant (tenant_id)`，但这需要 `0002_*.up.sql` 迁移，与本次澄清"不新增迁移"冲突，应另开特性。 |
| E2 | 🎯 | **删除部门与用户归属变更存在竞态，可产生孤儿引用**：`DELETE /admin/orgs/:id` 在事务内检查 `users WHERE dept_id = ?` 为 0 后删除；与此同时 `POST /admin/users` 或 `PATCH /admin/users/:id`（改 `deptId`）只做"部门存在"校验、不参与同一把锁。时序：删除方查得 0 → 用户创建方查得部门存在 → 删除提交 → 用户插入成功 → `users.dept_id` 指向已删除部门。规格的边界用例只覆盖了"删除父节点与创建子节点并发"，没有这一条。 | 让用户归属写入参与同一临界区，二选一：① 在 `UserService.CreateUser` / `UpdateUser`（改 `deptId` 时）对目标部门行加锁：`SELECT id FROM organizations WHERE id = ? FOR UPDATE`（与组织写操作的行锁冲突，自然串行化；成本一次索引查找）；② 或删除时对 `users` 按 `dept_id` 做锁定读（`idx_users_dept` 存在，RR 下会锁住该部门区间，阻塞新插入）。推荐 ①，语义最直观。同步在 spec 边界用例与 data-model INV-5 补这一条，并在 quickstart 增加"并发删部门 + 建用户"的验证。 |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 💡 | 512 字符路径兜底在 6 级上限下不可达：6 级 ID 型路径最大 `6×27+1 = 163` 字符。plan/data-model 保留了"路径长度兜底"规则，但实现时要么写死分支永远不触发，要么被误以为是有效防线。 | 删除该兜底规则，改为一条断言（`len(path) ≤ 512` 不满足即 `INTERNAL_ERROR` 并告警），并在 data-model §5 注明"由 6 级上限蕴含"。 |
| E4 | 💡 | `UPDATE ... SET path = CONCAT(...) WHERE path LIKE '旧前缀%'` 依赖 `LIKE` 前缀匹配。ULID 字符集不含 `%`/`_`，当前安全；但若将来 ID 生成策略改为允许下划线，会变成通配符注入式的误匹配（同前缀不同层级被误改）。 | 在 SQL 里显式转义（`ESCAPE '\\'`）或用范围比较 `path >= prefix AND path < prefixUpper`；在 `organization_store.go` 注释写明该前提。 |
| E5 | 💡 | 审计采用异步队列，"队列满丢弃"。组织变更属低频高价值事件，丢弃后无法追溯（例如误删难以复盘）。 | 保持现有异步设计（不阻塞主流程），但对 `org_*` 事件在入队失败时至少打 `Warn` 并带 `traceId`（现有 `Auditor` 已 warn，确认 detail 里有 orgId 即可）；无需改为同步写。 |

### Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | 💡 | 401/403 不写审计是本次决策，但 `Admin` 中间件对越权调用也不打日志。非管理员反复尝试组织写接口时，只有 403 响应，没有服务端线索（`traceId` 也无法反查）。 | 在 `middleware.Admin` 的拒绝分支加一条 `logger.Warn("admin endpoint forbidden", "user", u.Username, "path", c.FullPath(), "trace_id", ...)`；不改响应体、不写审计表，满足最小可观测性。 |
| E7 | 💡 | 威胁模型无新增面：端点都在 admin 组内、请求体无敏感数据、`tenantId` 被忽略避免越权。已核实无问题。 | 无需改动；建议在 contracts 中保留"`tenantId` 被忽略而非报错"这一条，避免实现者改成"接受并使用"。 |

### Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E8 | 💡 | 修改接口返回 `userCount`（该节点及子部门汇总）。若实现为"逐个节点 COUNT"，会产生 N+1；`CountUsersByDept` 已有全量分组统计，但按需求只适用于树接口。 | 在 store 提供 `CountUsersInSubtree(ctx, pathPrefix)`（一条 `SELECT COUNT(*) FROM users u JOIN organizations o ON o.id = u.dept_id WHERE o.path LIKE ?`），或在 service 复用 `CountUsersByDept` 的 map 后按前缀求和；契约里明确 `userCount` 的统计口径与树接口一致。 |
| E9 | 💡 | 500 节点全量锁 + 全表扫描（见 E1）在写操作上串行；读路径不受影响（MVCC），因此不会拖慢组织树查询。 | 与 E1 合并处理；在 plan 的性能目标里补一句"写操作串行、单次持锁毫秒级；读操作不加锁"。 |
