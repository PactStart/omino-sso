# Feature Specification: 应用管理详情子页面与授权体系

**Feature Branch**: `003-app-management-pages`

**Created**: 2026-10-21

**Status**: Draft

**Input**: User description: "应用管理页面，点击应用详情，不再展示抽屉，而是进入到子页面，左侧为菜单，右侧为内容区域，菜单分别是：1、应用详情…2、应用成员…3、应用角色…4、应用权限…5、授权管理…另外，获取用户信息接口 {issuer}/oauth2/userinfo（Bearer）需要返回用户在应用里的角色和权限点，都是字符串数组"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 应用详情子页面（导航改造 + 基本信息维护）(Priority: P1)

管理员在应用列表中点击某个应用的"详情"，不再弹出抽屉，而是进入该应用的独立子页面：左侧固定五个菜单（应用详情、应用成员、应用角色、应用权限、授权管理），右侧为对应内容区，默认停在"应用详情"；在详情页可查看应用基本信息，并对允许修改的字段就地编辑保存。

**Why this priority**: 抽屉的横向空间无法承载成员、角色、权限、授权四块内容，子页面是其余四个故事的唯一承载框架；没有它，后续功能无处安放。

[Describe this user journey in plain language]

**Acceptance Scenarios**:

1. **Given** 应用列表存在应用 A，**When** 点击 A 的"详情"，**Then** 进入 A 的子页面，左侧显示五个菜单且顺序固定，右侧为"应用详情"内容，页面上不再出现抽屉。
2. **Given** 处于 A 的子页面，**When** 刷新页面或把地址发给另一名管理员，**Then** 仍落在应用 A 的同一菜单页。
3. **Given** 在"应用详情"修改允许编辑的字段并保存，**When** 保存成功，**Then** 详情与列表中的对应信息立即一致，并生成一条审计记录。
4. **Given** 提交非法值（名称为空、地址格式非法、数值越界），**When** 点击保存，**Then** 拒绝保存并在对应字段就地提示，原值保持不变。
5. **Given** 查看应用标识、密钥等不允许修改的字段，**Then** 该字段为只读且无保存入口。

### User Story 2 - 应用成员管理与门户可见性 (Priority: P1)

管理员在"应用成员"页维护成员：支持按用户名、姓名、部门筛选"尚未加入"的用户并批量添加；支持批量移除，可跨分页全选与反选。成员关系成为门户"我的应用"的唯一可见性依据——只有成员才能看到并使用该应用。

**Why this priority**: 成员制是本次授权体系的基础：角色与权限都必须挂在"应用内的用户"上；同时它直接改变员工在门户中能看到什么，是用户可感知的核心变化。

**Independent Test**: 新建测试应用 B（不添加任何成员），用普通员工账号登录门户，确认"我的应用"不含 B；管理员把该员工加入 B 后重新进入门户，B 出现；移除后再查看，B 消失。

**Acceptance Scenarios**:

1. **Given** 应用 B 已有 2 名成员，**When** 打开"添加成员"弹窗并输入用户名片段，**Then** 结果只包含尚未加入 B 的用户，已加入的 2 人不出现在候选里。
2. **Given** 勾选 5 名候选用户并确认，**When** 提交成功，**Then** 列表新增 5 条成员记录，成员总数同步更新。
3. **Given** 候选中有 3 人已被他人并发加入，**When** 提交这 3 人，**Then** 不报错，返回"新增 0 人、已存在 3 人"，列表不产生重复记录。
4. **Given** 成员列表共 500 人、每页 20 人，**When** 在第 2 页执行"全选全部成员"并取消其中 1 人，**Then** 选中集合为其余 499 人，超出当前页范围。
5. **Given** 选中 3 名成员点击移除，**When** 确认框显示"将移除 3 名成员，并解除其在本应用的 7 项角色绑定"，确认后，**Then** 成员列表与计数同步，这 3 人的角色绑定同时消失。
6. **Given** 员工 E 不是应用 B 的成员，**When** E 登录门户查看"我的应用"，**Then** 不包含 B；管理员加入 E 后，E 重新进入门户即可见 B。

### User Story 3 - 应用角色管理 (Priority: P2)

管理员在"应用角色"页维护该应用内的角色：新建、查看、改名、改描述、删除；角色名称在应用内唯一，且只能由字母与数字组成；角色描述不超过 100 字。

**Why this priority**: 角色是把权限打包后授予成员的最小单位；没有角色，权限只能逐个授予成员，管理成本不可接受。

**Independent Test**: 在应用 B 中新建角色 `opsAdmin`，确认列表出现该角色；再尝试新建 `opsAdmin` 与 `ops-admin`，前者被拒（重名），后者被拒（含非法字符）；改名后再改回原名仍可用。

**Acceptance Scenarios**:

1. **Given** 应用 B 无角色，**When** 新建角色名 `opsAdmin`、描述"运维管理员"，**Then** 列表新增该角色，权限数与成员数均为 0。
2. **Given** 已存在 `opsAdmin`，**When** 再次新建 `opsAdmin`，**Then** 拒绝并提示"角色名已存在"，列表不变。
3. **Given** 输入角色名 `ops-admin` 或 `运维管理员`，**When** 提交，**Then** 拒绝并提示只允许字母与数字。
4. **Given** 描述输入 101 个字符，**When** 提交，**Then** 拒绝并提示长度上限 100 字。
5. **Given** 角色已绑定 3 个权限与 5 名成员，**When** 删除该角色，**Then** 确认框提示"将解除 3 项权限绑定与 5 名成员绑定"，确认后角色与其绑定一并消失。
6. **Given** 两个应用各自存在同名角色 `admin`，**Then** 二者互不冲突（唯一性仅在应用内生效）。

---

### User Story 4 - 应用权限管理（树形与列表）(Priority: P2)

管理员在"应用权限"页维护该应用的权限点：新建、查看、编辑、删除；权限点可按层级组织，页面提供树形与列表两种查看方式，切换后看到的是同一份数据。

**Why this priority**: 权限点是最终被判定"能做什么"的原子单位，角色只是它的集合；没有权限点，角色只有名字没有含义。

**Independent Test**: 在应用 B 中新建 `order:read`，再以 `order:read` 为父新建 `order:read:detail`；切到树形可见父子层级，切到列表可见两行且带父级列；删除父权限被拒并提示子节点数量。

**Acceptance Scenarios**:

1. **Given** 应用 B 无权限，**When** 新建编码 `order:read`、名称"订单查询"，**Then** 列表/树中新增该权限，父级为空、排序为默认值。
2. **Given** 已存在 `order:read`，**When** 以它为父新建 `order:read:detail`，**Then** 树形视图下表现为其子节点，列表视图下父级列显示 `order:read`。
3. **Given** 同一应用已存在 `order:read`，**When** 再次新建 `order:read`（大小写完全相同），**Then** 拒绝并提示编码已存在。
4. **Given** 选中父权限并删除，**When** 其下仍有 2 个子权限，**Then** 拒绝删除并提示"仍有 2 个子权限"。
5. **Given** 权限被 2 个角色引用，**When** 删除该权限，**Then** 确认框提示"将被 2 个角色解除引用"，确认后删除并解除引用。
6. **Given** 权限树含 30 个节点，**When** 在树形与列表之间切换，**Then** 数据条数与层级关系保持一致。

---

### User Story 5 - 授权管理（角色关联权限与成员）(Priority: P2)

管理员在"授权管理"页完成两类绑定：给角色分配权限、给角色分配成员；可以批量操作，也能一眼看出每个角色当前绑定了多少权限与多少成员。

**Why this priority**: 这是把角色、权限、成员三者真正连起来的页面；缺了它，前三个页面只是三份互不相关的清单。

**Independent Test**: 选角色 `opsAdmin`，一次勾选 3 个权限保存；再从成员列表勾选 2 名员工加入该角色；确认角色行的计数显示"3 个权限 / 2 名成员"，且这 2 人此前若不在应用成员中会被自动加入。

**Acceptance Scenarios**:

1. **Given** 角色 `opsAdmin` 无权限，**When** 在授权页勾选 3 个权限并保存，**Then** 角色行的权限计数变为 3，重复提交不会产生重复绑定。
2. **Given** 角色 `opsAdmin` 已有 3 个权限，**When** 取消其中 1 个并保存，**Then** 计数变为 2，其余权限不受影响。
3. **Given** 用户 U 不是应用成员，**When** 把 U 加入角色 `opsAdmin`，**Then** U 自动成为应用成员，页面提示"已同时加入 1 名成员"。
4. **Given** 角色 `opsAdmin` 绑定 2 名成员，**When** 移除其中 1 人，**Then** 该成员仍留在应用成员列表中，仅失去该角色。
5. **Given** 应用下有 20 个角色，**When** 在授权页搜索角色名片段，**Then** 只显示匹配角色，计数随之保持正确。

### User Story 6 - 用户信息接口返回应用内角色与权限点 (Priority: P2)

接入方用成员用户的访问令牌调用用户信息接口，除既有资料外，还能拿到该用户在该应用内的角色名与权限编码，均为字符串数组。

**Why this priority**: 这是本次授权体系对外兑现价值的地方——接入系统靠它做功能级鉴权；没有它，后台配置的角色与权限只是"看不见的数据"。

**Independent Test**: 用户 U 在应用 B 中被授予角色 `opsAdmin`（含权限 `order:read`、`order:write`），用 B 的访问令牌调用用户信息接口，确认返回 `app_roles: ["opsAdmin"]`、`permissions: ["order:read","order:write"]`；把 U 移出应用后再次调用，两个数组均为空。

**Acceptance Scenarios**:

1. **Given** U 是 B 的成员且有角色 `opsAdmin`（2 个权限），**When** 用 B 的令牌调用用户信息接口，**Then** 返回既有字段 + `app_roles: ["opsAdmin"]` + 两个权限编码。
2. **Given** U 同时拥有 2 个角色且权限有重叠，**When** 调用，**Then** `app_roles` 含两个角色名，`permissions` 为去重后的并集。
3. **Given** U 是成员但未分配任何角色，**When** 调用，**Then** `app_roles` 与 `permissions` 均为空数组（不是 null）。
4. **Given** U 在两个应用各有不同角色，**When** 分别用两个应用的令牌调用，**Then** 各自返回该应用内的角色与权限，互不混淆。
5. **Given** 管理员刚移除 U 的角色，**When** U 立即再次调用（无缓存等待），**Then** 返回结果已不含该角色及其权限。
6. **Given** 调用方未携带令牌或令牌无效，**Then** 行为与现状一致（拒绝），不因新增字段而改变。

---

### Edge Cases

- 应用暂无成员时（含上线初期的存量应用）：门户对所有人不可见（管理员本人若未加入也看不到）；成员页 MUST 显式提示"当前无成员，员工在门户将看不到该应用"，并提供批量添加入口。
- 同一用户被重复添加：不产生重复记录，不报错，返回实际新增数与已存在数。
- 角色改名后：已登录成员下一次调用用户信息接口即返回新名称；历史审计记录保留旧名称。
- 权限编码大小写差异（`order:read` 与 `ORDER:READ`）：视为两个不同权限（唯一性区分大小写），保存时若与既有编码仅大小写不同需提示确认。
- 两名管理员同时编辑同一角色的权限：后保存者被拒绝（`409`），页面提示"该角色已被他人修改，请刷新"，前端重新加载后再提交，不静默覆盖。
- 权限树的父级选择：禁止选择自身或自己的后代，避免形成环。
- 应用被停用：成员、角色、权限关系保留，但门户不再展示该应用。
- 候选成员在提交瞬间被删除账号：跳过该用户并在结果中提示"1 名用户已不存在"。
- 用户信息接口调用的令牌缺少应用上下文（例如仅申请基础身份范围）：`app_roles` 与 `permissions` 返回空数组，不报错。
- 权限层级过深（超过 6 层）：仍可保存与展示，但页面默认折叠第 4 层以下节点。

## Requirements *(mandatory)*

### Functional Requirements

**导航与详情**

- **FR-001**: 应用列表的"详情"入口 MUST 变更为进入独立子页面，MUST NOT 再打开抽屉；子页面左侧为菜单区、右侧为内容区，菜单固定为"应用详情、应用成员、应用角色、应用权限、授权管理"五项，顺序不可变。
- **FR-002**: 子页面 MUST 支持地址直达与刷新保持当前应用与当前菜单；MUST 提供返回应用列表的入口。
- **FR-003**: "应用详情"页 MUST 展示：应用标识、名称、描述、Logo、首页地址、回调地址、登出地址、授权方式、可申请范围、访问令牌有效期、刷新令牌有效期、启用状态、创建时间。
- **FR-004**: "应用详情"页 MUST 允许编辑以下字段：名称、描述、Logo 地址、回调地址、登出地址、访问令牌有效期、刷新令牌有效期、启用状态；保存成功后详情与列表 MUST 立即一致，并写入审计。调整令牌有效期时 MUST 提示"仅对此后签发的令牌生效，已签发令牌不受影响"。把启用状态改为停用时 MUST 二次确认，并提示"停用后全员在门户不可见，成员与角色配置保留"。
- **FR-005**: 应用标识与客户端密钥 MUST 在详情页只读、且密钥 MUST NOT 在页面明文展示；密钥轮换沿用既有独立入口。
- **FR-006**: 非法输入（名称为空或超长、地址非合法 URL、有效期越界）MUST 被拒绝：原值不变、字段就地提示、不写审计成功记录。

**成员**

- **FR-007**: "应用成员"页 MUST 分页展示成员的用户名、姓名、部门、加入时间、已分配角色数，并显示成员总数。
- **FR-008**: 添加成员 MUST 提供候选筛选，支持按用户名、姓名、部门三个条件筛选，且候选结果 MUST 只包含尚未成为该应用成员的用户。
- **FR-009**: 添加成员 MUST 支持一次提交多名用户；对已存在的成员 MUST 幂等（不报错、不重复插入），并返回新增数与已存在数。
- **FR-010**: 移除成员 MUST 支持逐条勾选、跨分页全选与反选；确认 MUST 显示待移除人数及将连带解除的角色绑定数量。
- **FR-011**: 移除成员 MUST 同步解除该成员在本应用内的全部角色绑定。
- **FR-012**: 门户"我的应用" MUST 只返回"该用户是成员且应用处于启用状态"的应用；非成员 MUST 看不到该应用，即使其在该应用下留有角色绑定。
- **FR-013**: 成员制 MUST 对全部应用一律生效，包含存量应用；系统 MUST NOT 自动把存量用户加入存量应用，MUST NOT 提供"全员可见/公开应用"例外开关。上线后存量应用对非成员员工不可见，管理员 MUST 能通过成员页的批量添加完成补员。
- **FR-014**: 成员账号被停用（`status≠1`）时 MUST 保留成员关系、在成员列表标记"已停用"，且 MUST NOT 允许再向其分配新角色；本系统不提供物理删除用户（`AGENTS.md` §6.1"删除用户 = 置 `status=0`"），因此不涉及删除级联。若未来引入物理删除，删除路径 MUST 在同一事务内清理其成员关系与角色绑定。

**角色**

- **FR-015**: "应用角色"页 MUST 支持角色的新增、查看、编辑（名称与描述）、删除，列表 MUST 显示角色名、描述、权限数、成员数、创建时间。
- **FR-016**: 角色名称 MUST 在应用内唯一、MUST 仅由字母与数字组成、trim 后长度 MUST 为 1–32 字符。
- **FR-017**: 角色描述 MUST 不超过 100 个字符（可为空）。
- **FR-018**: 删除角色 MUST 先解除其权限绑定与成员绑定，确认框 MUST 提示受影响数量；MUST NOT 因删除角色而删除成员本身。

**权限**

- **FR-019**: "应用权限"页 MUST 支持权限点的新增、查看、编辑、删除，字段包括权限编码、名称、描述、父级、排序。
- **FR-020**: 权限编码 MUST 在应用内唯一（区分大小写）、MUST 仅由字母、数字与 `_`、`-`、`.`、`:` 组成、长度 MUST 为 1–64 字符。
- **FR-021**: 权限 MUST 支持可选父级以形成层级，并在同一应用内构成树。"应用权限"页 MUST 提供树形与列表两种视图，二者展示同一份数据，切换视图 MUST NOT 改变数据；本次 MUST NOT 提供"按组织架构授权"（不把部门或人员作为权限的授予对象）。
- **FR-022**: 删除仍有子权限的权限 MUST 被拒绝并提示子节点数量；删除被角色引用的权限 MUST 提示引用角色数，确认后删除并同步解除引用。
- **FR-023**: 权限的父级选择 MUST 禁止选择自身及其后代，避免形成环。

**授权**

- **FR-024**: "授权管理"页 MUST 支持两类绑定：给角色分配/取消权限（可批量勾选，权限以树形或列表呈现），给角色分配/取消成员（可批量勾选）。
- **FR-025**: 把用户分配给角色时，若该用户尚不是应用成员，系统 MUST 自动将其加入成员，并在页面明确提示；MUST NOT 出现"有角色但不是成员"的状态。
- **FR-026**: 授权页 MUST 显示每个角色已绑定的权限数与成员数，并支持按角色名搜索。

**用户信息接口**

- **FR-027**: 用户信息接口 MUST 新增 `app_roles`（应用内角色名称数组）与 `permissions`（权限编码数组）两个字段；无角色或无权限时 MUST 返回空数组，MUST NOT 返回 null 或省略。已有 `roles` 字段承载平台级角色（`users.roles`），语义 MUST 保持不变、MUST NOT 被应用内角色覆盖（见 [research.md](./research.md) R1）。
- **FR-028**: `app_roles` 与 `permissions` MUST 按调用所用令牌所属的应用计算；同一用户在不同应用下的结果 MUST 相互独立。
- **FR-029**: 既有用户信息字段与 OIDC 其它端点行为 MUST 保持不变（本次为纯新增字段，不改变既有字段含义与类型）。
- **FR-030**: 成员关系、角色或权限变更后，下一次调用用户信息接口 MUST 立即反映最新结果（不依赖缓存刷新）。

**审计**

- **FR-031**: 成员增删、角色增删改、权限增删改、授权变更 MUST 写入审计日志，包含操作者、目标应用、目标对象与结果；且 MUST 可按应用与事件类型筛选。审计详情 MUST NOT 包含客户端密钥。
- **FR-032**: 应用列表 MUST 展示每个应用的成员数，并提供"仅看无成员应用"的筛选，使管理员能在上线前一次性定位所有待补员的应用（配合 FR-013 的"不自动补员"）。
- **FR-033**: "应用成员"页 MUST 提供"按部门加入"能力：选中一个部门（含其子部门）后，可一次把该部门下全部尚未加入的用户加入本应用，结果按"新增/已存在/已停用"分别计数。
- **FR-034**: 应用详情编辑、角色编辑、权限编辑与两类授权写入 MUST 支持携带读取时的版本（`updatedAt`）；携带且与服务端当前值不一致时 MUST 拒绝写入并提示"已被他人修改，请刷新后重试"，避免静默覆盖他人配置。管理后台前端 MUST 始终携带；未携带时视为不做版本校验（兼容脚本调用）。
- **FR-035**: 员工在门户没有任何可见应用时，MUST 展示空状态说明与"联系管理员开通"的引导文案，MUST NOT 只显示空白列表。
- **FR-036**: "应用角色"页 MUST 明确标注"应用内角色仅在本应用生效，与平台角色（`roles`）无关"，避免管理员与接入方混淆两套角色。
- **FR-037**: 审计 MUST 在地址类字段（回调地址、登出地址）变更时记录变更前后的完整取值（这些值本就存在于配置中，不属敏感数据）；删除角色或权限时 MUST 记录被连带解除的绑定快照（被解除的权限 ID / 成员 ID 清单；超过 20 项时记数量 + 前 20 项），使误删后可按审计手工恢复。

### Key Entities *(include if feature involves data)*

- **应用成员**：表示"某用户是某应用的成员"。关键属性包括所属应用、用户、加入时间、加入者；同一应用与用户的组合唯一。
- **应用角色**：表示应用内的一个职责集合。关键属性包括所属应用、角色名、描述、创建时间；同一应用内角色名唯一。
- **应用权限**：表示应用内的一个原子能力。关键属性包括所属应用、权限编码、名称、描述、父级权限、排序；同一应用内编码唯一，父级构成层级。
- **角色-权限绑定**：表示某角色拥有某权限；同一角色与权限的组合唯一。
- **角色-成员绑定**：表示某成员被授予某角色；同一角色与成员的组合唯一，且该成员 MUST 同时是应用成员。
- **可见性规则**：门户"我的应用"由应用成员关系与启用状态共同决定，取代"所有启用应用对所有人可见"的现状。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一名熟悉后台的管理员可在 3 分钟内完成"进入应用子页面 → 新建角色 → 绑定 3 个权限 → 加入 2 名成员 → 在门户确认可见"的完整闭环。
- **SC-002**: 应用有 500 名成员、候选池 10,000 名用户时，成员列表首屏与候选筛选结果的返回时间均不超过 1 秒。
- **SC-003**: 连续抽查 20 组"角色-权限-成员"配置，用户信息接口返回的角色与权限与授权管理页展示 100% 一致；解除绑定后下一次调用即生效，无陈旧数据。
- **SC-004**: 权限树在 200 个节点规模下，树形与列表之间的切换、以及展开/收起全部，均在 1 秒内完成且无节点错位。
- **SC-005**: 在 500 条成员数据下执行"跨分页全选后再反选 1 人"，实际移除的对象与界面显示的数量 100% 一致，无漏删或误删。
- **SC-006**: 本次变更对既有应用列表、登录、门户其它功能零回归：现有自动化测试全部通过，员工日常登录与单点登录流程不受影响。
- **SC-007**: 上线两周内，≥80% 的启用应用完成成员配置且至少配置 1 个角色；管理员通过"仅看无成员应用"筛选，能在 5 分钟内列出全部待补员应用。
- **SC-008**: 若上线一周内出现 ≥5 起"员工看不到应有应用"的工单，触发回滚评审（评估是否临时恢复"全员可见"，或以配置方式加白名单），并由产品与运维共同决策。

## Assumptions

- 这些页面只对管理员开放；普通员工不进入管理后台，只感知门户"我的应用"的变化。
- 应用成员制对全部应用一律生效，存量应用不自动补员（见 FR-013）：上线后由管理员通过成员页批量添加成员，期间未补员的应用对普通员工不可见属预期行为。
- 权限只通过角色授予成员，不按组织架构（部门/人员）直接授权；组织架构仅用于成员列表与候选人筛选。
- 权限点由管理员手工维护，不从接入系统代码或接口描述自动同步；权限点与 OIDC 的 `scope` 是两套独立概念，本次不建立映射。
- 角色名与权限编码由管理员填写，系统不自动生成，也不做多语言展示。
- 门户本期只按成员关系过滤应用清单，不展示"我在该应用中的角色"；角色信息仅通过用户信息接口对外提供。
- `app_roles` 与 `permissions` 均为去重后的并集：一个成员拥有多个角色时，权限取并集。
- 应用成员、角色、权限、绑定的删除均为即时生效的硬删除，不引入回收站或软删除。
- 移动端与窄屏仅保证可操作，不做专门适配；管理后台以桌面浏览器为主。
- 租户概念沿用现状：本次不引入跨租户的成员共享或权限共享。
- 应用停用采用"二次确认 + 影响提示"（普通确认框），不要求输入应用标识；若后续需要更强的防误触保护，另行评估。
- 交付顺序按价值拆分：先交付"子页面 + 详情 + 成员（含门户可见性）"，再交付"角色 + 权限 + 授权 + userinfo 字段"，具体批次在 plan 中固化。
