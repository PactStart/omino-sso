# Feature Specification: 多通道验证与账号安全

**Feature Branch**: `005-verification-code-auth`

**Created**: 2026-10-22

**Status**: Draft

**Input**: User description: "portal 支持绑定/修改手机号与邮箱（短信/邮箱验证码）；登录方式扩展到用户名/邮箱/手机号 + 密码，以及邮箱/手机验证码登录；支持找回与重置密码；支持 MFA 绑定与解绑；管理后台增加短信/邮箱发送记录；支持验证码模拟发送。短信供应商抽象（先创蓝，后续可扩展），邮件模板走文件与配置。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 绑定与修改手机号、邮箱 (Priority: P1)

员工在账号中心（portal）维护自己的联系方式：未绑定时可绑定手机号或邮箱，已绑定时可修改。绑定或修改都必须通过对应渠道的验证码验证归属，防止误绑他人联系方式。

**Why this priority**: 手机号与邮箱是验证码登录、找回密码、MFA 解绑的信任基础。没有可信的联系方式，后续所有验证码能力都无法成立，因此是本特性的地基。

**Independent Test**: 员工登录后进入账号中心，绑定一个手机号（输入手机号 → 收验证码 → 提交），页面立即显示已绑定状态；随后修改该手机号（新手机号收验证码 → 提交）也即时生效。此故事可独立交付，不依赖其他故事。

**Acceptance Scenarios**:

1. **Given** 员工已登录且尚未绑定手机号，**When** 输入手机号、获取并提交短信验证码，**Then** 手机号绑定成功并在账号中心显示。
2. **Given** 员工已登录且尚未绑定邮箱，**When** 输入邮箱、获取并提交邮箱验证码，**Then** 邮箱绑定成功并在账号中心显示。
3. **Given** 员工已绑定手机号，**When** 修改为新手机号并通过新手机号验证码，**Then** 手机号更新为新值。
4. **Given** 员工已绑定邮箱，**When** 修改为新邮箱并通过新邮箱验证码，**Then** 邮箱更新为新值。
5. **Given** 员工输入已被他人占用的手机号或邮箱，**When** 提交验证码，**Then** 系统拒绝并提示该联系方式已被使用。

---

### User Story 2 - 多方式登录（密码 / 邮箱验证码 / 手机验证码） (Priority: P1)

用户在登录页可以使用用户名、邮箱或手机号配合密码登录，系统按输入格式自动识别账号类型；也可以切换为邮箱验证码登录或手机验证码登录，无需记忆密码。

**Why this priority**: 登录是员工使用系统的第一道门槛。支持邮箱/手机号登录降低记忆成本，验证码登录则在忘记密码时仍能进入系统，是核心入口能力。

**Independent Test**: 在登录页分别用「邮箱 + 密码」「手机号 + 密码」「邮箱 + 验证码」「手机 + 验证码」四种方式登录同一账号，均能成功进入门户。可独立交付与验证。

**Acceptance Scenarios**:

1. **Given** 用户已绑定邮箱，**When** 输入邮箱 + 密码提交，**Then** 系统识别为邮箱方式并登录成功。
2. **Given** 用户已绑定手机号，**When** 输入手机号 + 密码提交，**Then** 系统识别为手机号方式并登录成功。
3. **Given** 用户在登录页切换到邮箱验证码登录，**When** 输入邮箱并提交收到的验证码，**Then** 登录成功。
4. **Given** 用户在登录页切换到手机验证码登录，**When** 输入手机号并提交收到的验证码，**Then** 登录成功。
5. **Given** 用户输入的账号未绑定对应的邮箱/手机号（验证码登录），**When** 提交，**Then** 系统拒绝并给出明确提示。

---

### User Story 3 - 找回与重置密码 (Priority: P1)

忘记密码的用户可在登录页通过邮箱验证码或手机验证码找回（重置）密码；已登录用户也可在账号中心通过验证码重新设置密码。

**Why this priority**: 找回密码是账号自助闭环的关键，直接影响员工在丢失凭据后能否恢复访问，同时降低 IT 人工重置的负担。

**Independent Test**: 在登录页选择「忘记密码」，通过邮箱验证码完成密码重置后，用新密码登录成功；同样流程通过手机验证码也可完成。可独立交付与验证。

**Acceptance Scenarios**:

1. **Given** 用户在登录页选择找回密码，**When** 通过邮箱验证码验证并设置新密码，**Then** 重置成功，可用新密码登录。
2. **Given** 用户在登录页选择找回密码，**When** 通过手机验证码验证并设置新密码，**Then** 重置成功，可用新密码登录。
3. **Given** 已登录用户在账号中心，**When** 通过邮箱或手机验证码重新设置密码，**Then** 密码更新，且该账号在其他设备上的会话被登出。

### User Story 4 - MFA 绑定与解绑 (Priority: P2)

员工在账号中心的「安全状态」区域管理多因素认证（MFA）：未绑定时展示「绑定」入口，点击后弹出二维码，用支持 TOTP 的设备扫码并填写 6 位动态码验证后完成绑定；已绑定时展示「解绑」入口，通过手机短信验证码或邮箱验证码验证后解绑。

**Why this priority**: MFA 显著提升账号安全等级，但依赖账号中心的基础交互与验证码通道，故排在基础能力之后。

**Independent Test**: 员工在账号中心点击绑定，扫码后填写 6 位动态码完成绑定，状态变为「已绑定」；再通过短信验证码解绑，状态回到「未绑定」。可独立交付与验证。

**Acceptance Scenarios**:

1. **Given** 未绑定 MFA 的员工，**When** 点击绑定、扫码并填写正确的 6 位动态码，**Then** MFA 绑定成功，安全状态显示「已启用」。
2. **Given** 未绑定 MFA 的员工，**When** 填写错误的 6 位动态码，**Then** 绑定失败并给出提示，不改变绑定状态。
3. **Given** 已绑定 MFA 的员工，**When** 通过手机短信验证码或邮箱验证码验证后解绑，**Then** MFA 解绑成功，安全状态显示「未启用」。
4. **Given** 已绑定 MFA 的员工，**When** 登录，**Then** 需完成 MFA 二次验证后才能进入系统（与既有二步验证机制一致）。

---

### User Story 5 - 短信/邮箱发送记录 (Priority: P2)

管理员在后台能够分页查看所有短信与邮箱验证码的发送记录（渠道、场景、接收方、结果、时间等），用于审计与排障。

**Why this priority**: 发送记录是验证码类能力的治理与审计支撑，可独立于具体验证码业务交付。

**Independent Test**: 系统产生若干发送记录后，管理员在后台发送记录页分页浏览并按渠道/场景/结果筛选。可独立交付与验证。

**Acceptance Scenarios**:

1. **Given** 系统存在若干短信/邮箱发送记录，**When** 管理员打开发送记录页，**Then** 以分页形式看到每条记录的渠道、场景、接收方、结果、时间等信息。
2. **Given** 存在多种场景与结果的记录，**When** 管理员按渠道/场景/结果/时间筛选，**Then** 列表正确过滤。

---

### User Story 6 - 验证码模拟发送（开发/测试配置） (Priority: P3)

系统通过配置决定短信与邮箱是否走真实发送还是模拟发送；开启模拟发送后，验证码统一为固定值「6 个 8」，不产生真实短信/邮件费用与外部依赖。

**Why this priority**: 模拟发送让开发、测试与演示环境无需真实短信/邮件供应商即可完整跑通验证码流程，是降低交付成本与外部依赖的辅助能力。

**Independent Test**: 开启模拟发送配置后，任意验证码请求都返回固定验证码「6 个 8」，且不触发真实供应商调用。可独立验证。

**Acceptance Scenarios**:

1. **Given** 配置开启模拟发送，**When** 用户请求任意验证码，**Then** 验证码固定为「6 个 8」且不产生真实短信/邮件。
2. **Given** 配置关闭模拟发送，**When** 用户请求验证码，**Then** 走真实供应商发送并返回真实验证码。

---

### Edge Cases

- 验证码过期（超过有效期）或重复使用：系统必须拒绝，不重复生效。
- 验证码请求过于频繁：系统必须限流，防止短信/邮件轰炸与费用滥用。
- 手机号/邮箱已被其他账号占用：绑定或修改必须拒绝并提示。
- 未登录用户发起验证码登录/找回密码：必须配合图形验证码等防刷措施，避免批量探测账号。
- 验证码登录/找回密码的目标账号不存在或未绑定对应联系方式：给出统一、不泄露账号存在性的提示。
- 短信/邮件供应商不可用或发送失败：系统必须给出可理解提示并记录失败结果，不误判验证码有效。
- 绑定 MFA 后设备遗失或动态码失效：可通过验证码解绑恢复，避免账号被锁死。
- 模拟发送与真实发送同时并存的风险：通过配置显式隔离，禁止在生成环境误开启模拟发送。
- 存量账号：历史上无手机号/邮箱的账号，在绑定前无法使用验证码登录与找回，需明确提示其先通过密码登录后绑定。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 员工 MUST 能在账号中心绑定手机号，且必须通过短信验证码验证归属。
- **FR-002**: 员工 MUST 能在账号中心绑定邮箱，且必须通过邮箱验证码验证归属。
- **FR-003**: 员工 MUST 能修改已绑定的手机号或邮箱，修改时必须再次通过新联系方式对应的验证码验证。
- **FR-004**: 手机号与邮箱在系统内 MUST 唯一，绑定或修改时须校验并拒绝重复。
- **FR-005**: 系统 MUST 支持以用户名、邮箱或手机号任一方式配合密码登录，并按输入格式自动识别账号类型。
- **FR-006**: 系统 MUST 支持邮箱验证码登录。
- **FR-007**: 系统 MUST 支持手机号验证码登录。
- **FR-008**: 登录页 MUST 提供登录方式切换能力（密码登录 / 邮箱验证码登录 / 手机验证码登录）。
- **FR-009**: 用户 MUST 能通过邮箱验证码或手机验证码找回（重置）密码；重置成功后不自动登录，用户须使用新密码重新登录。
- **FR-010**: 已登录用户 MUST 能通过邮箱验证码或手机验证码重新设置密码，重置后应使其其他设备会话失效。
- **FR-011**: 短信发送 MUST 通过供应商抽象实现，首个支持供应商为创蓝，结构须支持后续扩展其他供应商（如阿里云）而不改动调用方。
- **FR-012**: 邮箱验证码邮件模板 MUST 以文件形式存储并根据配置读取；服务端 Docker 镜像构建时 MUST 一并复制该模板文件。
- **FR-013**: 系统 MUST 记录每次短信与邮箱验证码的发送记录，字段至少含渠道、场景、接收方、结果与时间。
- **FR-014**: 管理员 MUST 能在后台分页查看发送记录，并支持按渠道/场景/结果等条件筛选。
- **FR-015**: 员工 MUST 能在账号中心绑定 TOTP 类 MFA（展示二维码，扫码后填写 6 位动态码验证）。
- **FR-016**: 已绑定 MFA 的员工 MUST 能通过手机短信验证码或邮箱验证码解绑 MFA；未绑定时展示绑定入口。
- **FR-017**: 系统 MUST 通过配置决定短信与邮箱是否模拟发送；开启模拟发送时验证码统一为「6 个 8」，且不触发真实供应商发送。
- **FR-018**: 验证码 MUST 具有有效期，过期或重复使用必须拒绝；连续错误尝试超过 5 次后该验证码 MUST 立即失效。
- **FR-019**: 验证码请求 MUST 具备发送频率限制，防止滥用与费用损耗。
- **FR-020**: 验证码登录、找回密码、MFA 绑定/解绑等操作 MUST 记录审计日志（操作者、对象、结果、时间）。

### Key Entities *(include if feature involves data)*

- **发送记录（Send Record）**: 一次短信或邮箱验证码发送产生的记录，含渠道（短信/邮箱）、场景（绑定/登录/找回/解绑等）、接收方、结果（成功/失败）、供应商、时间等。
- **验证码（Verification Code）**: 一次性临时凭证，关联渠道、场景、目标联系方式与有效期，用于证明联系方式归属。
- **用户（User）**: 扩展手机号、邮箱与 MFA 绑定状态；手机号与邮箱全局唯一。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 员工完成手机号或邮箱绑定（含验证码获取与验证）的总耗时不超过 2 分钟。
- **SC-002**: 用户在验证码有效期内，通过验证码登录或找回密码的一次成功率不低于 95%。
- **SC-003**: 过期或重复使用的验证码被拒绝的比例为 100%。
- **SC-004**: 开启模拟发送后，验证码为固定值「6 个 8」的比例为 100%，且不产生真实短信/邮件。
- **SC-005**: 每次短信/邮箱发送产生一条可追溯发送记录的比例为 100%。
- **SC-006**: 绑定 MFA 后登录强制二次验证，解绑后恢复单步验证，状态切换即时生效。

## Assumptions

- **验证码有效期与频率（合理默认）**: 验证码默认 5 分钟有效，同一目标联系方式 60 秒内不可重复发送；具体阈值在计划阶段细化。
- **联系方式唯一性**: 一个手机号/邮箱只能归属一个账号，绑定与修改时校验。
- **手机号格式**: 仅支持中国大陆手机号（11 位数字，默认 +86），不支持国际号码。
- **联系方式脱敏**: 手机号与邮箱的脱敏由服务端完成，接口返回即为脱敏数据；前端不做二次脱敏处理。
- **MFA 与登录关系**: 绑定 MFA 后，登录流程触发既有 MFA 二次验证；本特性聚焦绑定/解绑入口，不重构登录二步验证状态机。
- **验证码登录范围**: 验证码登录仅面向已注册且已绑定对应联系方式的账号，本特性不引入「验证码首次登录即注册」。
- **存量账号兼容**: 历史上未绑定手机号/邮箱的账号，需先通过密码登录后到账号中心绑定，方可使用验证码登录与找回。
- **短信供应商**: 首个实现创蓝；供应商抽象与配置结构为后续接入阿里云等预留扩展，本期不实现其他供应商。
- **邮件模板**: 验证码邮件模板以文件形式存在并由配置指定路径，Docker 镜像打包时一并包含。
- **未登录防刷**: 验证码登录与找回密码等未登录流程须配合图形验证码防刷，与既有登录图形验证码机制一致。
- **发送记录保留策略**: 短信/邮箱发送记录与审计日志均保留 6 个月，过期由系统内置定时任务（服务启动时开启）自动清理，不引入外部分布式定时任务框架。

## Clarifications

### Session 2026-10-22

- Q: 用户在登录页通过邮箱/手机验证码找回（重置）密码成功后，系统应自动登录该用户，还是要求其使用新密码重新登录？ → A: 要求使用新密码重新登录（不自动登录）。
- Q: 单个验证码是否应限制最大连续错误尝试次数，超过后该验证码立即失效、需重新获取？ → A: 限制，连续错误 5 次后该验证码立即失效。
- Q: 手机号的支持范围是仅中国大陆号码，还是需要支持国际号码（含国家/地区区号）？ → A: 仅中国大陆手机号（11 位，默认 +86）。
- Q: 手机号与邮箱在账号中心等界面展示时，是否进行脱敏？ → A: 脱敏展示，且由服务端返回脱敏数据，前端不做二次脱敏处理。
- Q: 短信/邮箱发送记录需要保留多久，是否有归档或清理策略？ → A: 发送记录与审计日志均保留 6 个月，由系统内置定时任务（启动时开启）自动清理，不引入外部定时任务框架。
