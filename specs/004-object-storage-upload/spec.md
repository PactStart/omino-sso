# Feature Specification: 图片上传与对象存储（头像与 Logo）

**Feature Branch**: `004-object-storage-upload`

**Created**: 2026-10-21

**Status**: Draft

**Input**: User description: "图片上传与对象存储 FileStore 抽象——员工自助上传头像、管理员上传应用 logo；首选阿里云 OSS，前端直传。来源：评估 object-storage-upload（见 `.specify/assessments/object-storage-upload/`）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 管理员上传与管理应用 Logo (Priority: P1)

管理员在管理后台注册或编辑应用时，不再需要自行在系统外托管图片再粘贴 URL，而是直接在系统内选择图片、裁剪后上传作为应用 logo；上传后 logo 立即可用于门户展示；管理员可随时替换或清除。

**Why this priority**: 应用 logo 是「我的应用」门户与登录体验的门面，且当前现状（外部托管 + 粘贴 URL）的痛点最明确、界面已存在，落地即可消除一段人工链路，是价值密度最高、最独立可交付的一块。

**Independent Test**: 管理员在应用管理中裁剪并上传一张合规图片作为 logo，保存后无需任何外部托管即可在「我的应用」列表看到该 logo；随后替换与清除均能即时生效。此故事可独立于头像功能单独交付。

**Acceptance Scenarios**:

1. **Given** 管理员在应用创建/编辑界面，**When** 选择一张合规图片并提交，**Then** 系统接受该图片、保存应用，并返回可直接访问的 logo 地址。
2. **Given** 组件启用了裁剪且管理员选择的图片尺寸较大，**When** 裁剪选择矩形区域后上传，**Then** 系统保存裁剪后的图片作为 logo。
3. **Given** 某应用已有 logo，**When** 管理员上传新图片替换，**Then** 新 logo 立即展示，旧 logo 不再对外可访问。
4. **Given** 某应用已有 logo，**When** 管理员清除 logo，**Then** 门户回退为名称首字占位，且原 logo 不再对外可访问。
5. **Given** 管理员上传不合规图片（如超限大小），**When** 提交，**Then** 系统拒绝并给出可理解提示，且不产生任何悬挂资源。

---

### User Story 2 - 员工自助上传与更新头像 (Priority: P2)

员工在账号中心查看个人资料时，能够裁剪并上传自己的头像（当前头像完全只读）；上传后头像立即更新展示；员工可替换或清除头像，清除后回退为姓名首字占位。管理员亦可在后台为用户设置或清除头像。

**Why this priority**: 头像只读是产品文档明确记录的缺口（`avatarUrl` 无上传接口），开通自助头像能补齐「统一身份门户」的体验断档；相较 logo 稍低优先级，是因为它不阻塞任何接入系统的展示链路。

**Independent Test**: 员工在账号中心裁剪并上传一张合规图片作为头像，页面立即展示新头像；替换与清除均即时生效。此故事可独立于 logo 功能单独交付。

**Acceptance Scenarios**:

1. **Given** 员工在账号中心且当前头像为空，**When** 上传一张合规图片，**Then** 头像立即展示该图片。
2. **Given** 组件启用了裁剪且员工选择的图片尺寸较大，**When** 裁剪选择矩形区域后上传，**Then** 头像保存为裁剪后的图片。
3. **Given** 员工已有头像，**When** 上传新图片替换，**Then** 头像更新为新图片，旧头像不再对外可访问。
4. **Given** 员工已有头像，**When** 清除头像，**Then** 头像回退为姓名首字占位，原头像不再对外可访问。
5. **Given** 员工尝试上传不合规图片，**When** 提交，**Then** 系统拒绝并给出可理解提示，不产生悬挂资源。
6. **Given** 管理员在后台用户管理，**When** 为某用户设置或清除头像，**Then** 该用户头像相应更新或回退为姓名首字占位。

---

### User Story 3 - 图片失联时的优雅降级 (Priority: P3)

当任意 logo 或头像因被删除、替换或外部失效而无法加载时，展示方（门户「我的应用」、账号中心、管理后台列表）自动回退为占位符（名称首字方块 / 姓名首字），不出现破损图片。

**Why this priority**: 这是治理能力的兜底体验，不新增上传能力，但能保证替换/清除/失效场景下界面始终得体；优先级最低，因为它可在前两个故事之后独立补齐。

**Independent Test**: 将一个应用的 logo 清除或使其失效后，刷新「我的应用」列表，该应用图标显示为名称首字占位而非破损图标；账号中心头像同理。

**Acceptance Scenarios**:

1. **Given** 某应用的 logo 不可访问，**When** 用户打开「我的应用」，**Then** 该应用显示名称首字占位，无破损图标。
2. **Given** 某用户的头像不可访问，**When** 本人或他人查看其资料，**Then** 显示姓名首字占位，无破损图片。

---

### User Story 4 - 管理员查看与管理上传文件记录 (Priority: P3)

管理员在后台能够分页查看所有上传文件的记录（供应商、场景、格式、大小、链接、状态、创建人、创建时间），并更新某条记录的状态（如禁用、删除）。

**Why this priority**: 这是治理与审计的必要能力，支撑对上传资产的统一管控；与核心上传流程解耦，可独立交付，优先级与失联降级同档。

**Independent Test**: 管理员在后台上传文件管理页分页浏览记录，并对某条记录更新状态，列表与展示方相应生效。此故事可独立于上传组件细节交付。

**Acceptance Scenarios**:

1. **Given** 系统存在若干上传文件记录，**When** 管理员打开文件管理页，**Then** 以分页形式看到每条记录的供应商、场景、格式、大小、链接、状态、创建人、创建时间。
2. **Given** 某条文件记录当前为「生效」，**When** 管理员将其状态更新为「禁用」或「删除」，**Then** 该记录状态更新，且其关联的 logo/头像展示方相应失效或回退占位。

---

### Edge Cases

- 上传空文件、损坏文件或伪装成图片的非图片内容时，系统必须拒绝且不产生悬挂资源。
- 图片尺寸极大（远超展示所需）时的处理：拒绝或按约束提示，不导致展示异常；或先裁剪再上传。
- 裁剪区域过小或比例异常（裁剪启用时）：组件给出提示或禁用上传，避免产生无效图片。
- 同一用户/应用在极短时间内重复上传：以最后一次为准，旧资源按生命周期清理。
- 上传过程中网络中断或凭证失效：不产生半成品对象，用户可重新发起。
- 上传成功但回写业务字段失败（如后端接口异常）：给出可重试提示，不产生孤儿记录。
- 存量外部 URL（历史上已填的 logo/头像地址）在本次变更后继续有效展示。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 管理员 MUST 能够在应用管理中上传一张图片作为应用 logo，无需提供外部托管 URL。
- **FR-002**: 管理员 MUST 能够替换或清除已存在的应用 logo。
- **FR-003**: 员工 MUST 能够在账号中心上传一张图片作为自己的头像。
- **FR-004**: 员工 MUST 能够替换或清除自己的头像，清除后回退为姓名首字占位。
- **FR-005**: 系统 MUST 校验上传图片的格式与大小，不合规时拒绝并给出可理解的提示；安全防护仅限格式与大小校验，不做恶意/伪装文件的深度检测。
- **FR-006**: 上传成功后，系统 MUST 将图片的可访问地址关联到对应业务实体（应用 logo 或用户头像），供展示方使用。
- **FR-007**: 当 logo 或头像缺失或无法加载时，展示方 MUST 回退为占位符，不显示破损图片。
- **FR-008**: 替换或清除图片后，被替换/清除的旧图片 MUST 不再对外可访问。
- **FR-009**: 系统 MUST 执行访问控制：仅管理员可管理应用 logo；用户头像由员工本人（自助）与管理员（代管）共同管理。
- **FR-010**: 上传、替换、清除操作 MUST 记录审计日志（操作者、对象、结果、时间）。
- **FR-011**: 管理员 MUST 能够在后台为用户设置或清除头像，其效果与员工自助上传/清除等价。
- **FR-012**: 系统 MUST 为每次上传记录一条文件记录，字段含：供应商（provider）、场景（scene）、格式（format）、大小（size）、链接（url）、状态（status）、创建人（creator）、创建时间（createdAt）。
- **FR-013**: 文件记录的「场景」与「状态」MUST 为预定义的字符串枚举。
- **FR-014**: 管理员 MUST 能够在后台分页查看上传文件记录。
- **FR-015**: 管理员 MUST 能够更新文件记录的状态。
- **FR-016**: admin 与 portal MUST 复用行为一致的单文件上传组件（交互与裁剪行为完全一致）。
- **FR-017**: 上传完成后，前端 MUST 调用后端接口写入文件记录并回写业务表对应字段（应用 logoUrl / 用户 avatarUrl），随后回显图片（前端契约；服务端结果见 FR-006）。
- **FR-018**: 上传组件 MUST 支持在上传前对图片进行裁剪（选择矩形区域）；裁剪为可选能力，默认关闭，由调用方通过组件属性决定是否启用。

### Key Entities *(include if feature involves data)*

- **文件记录（File/Image Asset）**: 一次上传产生的一条记录，字段含供应商（provider）、场景（scene，字符串枚举）、格式（format）、大小（size）、链接（url）、状态（status，字符串枚举）、创建人（creator）、创建时间（createdAt）；归属一个应用 logo 或一个用户头像。
- **应用（OAuth Client）**: 拥有一个可选的 logo 图片资产。
- **用户**: 拥有一个可选的 avatar 图片资产。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 管理员为应用配置 logo 可在不离开系统、不经外部托管的情况下 100% 完成。
- **SC-002**: 员工上传头像到看到更新结果的时间不超过 1 分钟。
- **SC-003**: 上传合规图片后，logo 与头像在门户/账号中心立即可见、无破损。
- **SC-004**: 不合规图片被拒绝的比例为 100%，且不产生悬挂资源。
- **SC-005**: 门户与账号中心中因图片失联而显示破损图片的场景降为 0（全部回退占位）。
- **SC-006**: 每次上传均产生一条可追溯的文件记录（100%），管理员可据此分页查看与更新状态。

## Assumptions

- **图片约束（已澄清）**: 支持常见图片格式（JPG / PNG / WebP），单张大小上限 5MB；超限拒绝并提示。安全防护仅限格式与大小校验，不做恶意/伪装文件深度检测。精确阈值与格式清单在计划阶段细化。
- **访问策略（已澄清）**: 上传后的 logo 与头像公开可访问（无需登录即可查看），与当前外部 URL 现状一致；防盗链、私有读、CDN 加速等高级策略不在本期范围。
- **枚举取值（已定稿）**: 场景枚举 `app_logo`（应用 logo）/ `user_avatar`（用户头像）；状态枚举 `active`（生效）/ `disabled`（禁用）/ `deleted`（已删除）。
- **存量兼容（合理默认）**: 历史上以外部 URL 填写的 logo/头像继续有效展示，仅新上传走新流程，不强制迁移存量数据。
- **供应商（已澄清）**: 首选阿里云 OSS；后续扩展 OBS、COS、S3、MinIO 不属于本期范围。
- **对象存储抽象与配置（用户澄清）**: 对象存储抽象须灵活，配置由供应商（provider）决定——如 `provider=aliyun_oss` 需 `accessKeyId` / `accessSecret`，其他 provider 对应各自的配置项；本期仅实现阿里云 OSS，但抽象与配置结构需为后续扩展预留。
- **实现细节（留待计划阶段）**: 直传凭证机制、服务端 `FileStore` 接口边界、admin 与 portal 共享上传组件与裁剪器的具体实现，均属技术方案，由 `/speckit.plan` 决定，本规格不展开。
- **合规依赖**: 本功能须遵循项目宪法（`.specify/memory/constitution.md`）——凭证不出服务端、分层 `api → service → store`、结构变更走手写 SQL 迁移；新增对象存储依赖与基础设施须先更新 `AGENTS.md` §2 与 §3。

- Q: 上传后的头像与 logo 图片，其访问地址是公开可访问还是需登录才能查看？ → A: 公开可访问（无需登录即可查看）。

- 补充澄清（用户追加，2026-10-21）: 裁剪为非强制能力，默认关闭，由传入组件的属性决定是否启用。
- 补充澄清（用户追加，2026-10-21）: 对象存储抽象需灵活，配置由 provider 决定（如 `provider=aliyun_oss` 需 `accessKeyId` / `accessSecret`，其他 provider 各自配置）。
