## Executive Summary

方案本身是收敛的：四域名的职责、`api` 域只在服务端可见、admin 根路径化、探针暴露面、跨域回跳这些关键口径都在 clarify 阶段定死了，`plan.md` 的 D1–D9 与 `contracts/` 四份契约能对上，`api-evolve` 基线也确认契约面零变化（`openapi.json` sha256 必须保持不变，这条设计得很好）。

本轮用**代码事实**复查后，找到 4 项必须在实现前修正的问题，其中 3 项是"计划没写、但一写就会踩"的落地缺口，1 项是**本特性会引入的回归**：

1. 清 session cookie 的那一处没带 `Domain`（`me/profile.go:178`）。旧拓扑（host-only）下它是对的；新拓扑强制 `.example.com` 后，改密码会**清不掉**共享 cookie，四个域都还登着，且服务端 sid 未 revoke。
2. 一体化 compose 没有约定 dev 构建参数，产物里会写死生产域名 / `5173`，US3「本地与测试环境一致」直接不成立。
3. 探针会走全局 `RateLimit`（`router.go:47`），配额一旦调小就变成"探针 429 → 容器重启"的风暴。
4. `COOKIE_DOMAIN` 在 `prod` 没有非空校验（`config.go:301-308`），而它是新拓扑下最容易配错、后果最隐蔽的一项（宪法要求"必填项缺失必须非零退出"）。

产品侧没有方向性问题，但有一处**表述风险**（`api` 域被当成强制隔离边界，实际只是命名锚点）和一处**未决策的协议边界**（SP 的 `post_logout_redirect_uri` 能否绝对地址回跳），后者需要产品拍板。

### 4b. Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | **清 session cookie 未带 `Domain`，本特性会把它从"无害"变成"回归"**：`internal/api/me/profile.go:178` 是 `&http.Cookie{Name:"sid", Value:"", Path:"/", MaxAge:-1}`（无 `Domain`、也无 `SameSite`），而登录侧 `internal/api/auth/login.go:238-241` 与 `internal/oidc/login.go:238-241` 都带了 `Domain: cfg.CookieDomain`。新拓扑强制 `COOKIE_DOMAIN=.example.com` 后，`/me/password` 返回的 `Set-Cookie` 会创建一个 **host-only 空 cookie**，`.example.com` 上的真 cookie 依然有效；且该 handler 没有 revoke 服务端会话 → **改完密码后四个域仍全部登录**（安全语义错误，也让 FR-023 的"登出即失效"出现同类漏洞）。 | 抽 `clearSessionCookie(c, cfg)`（与 `setCookie` 同文件、复用 `CookieDomain/Secure/SameSite`），`ChangePassword` 在响应前 `sessions.Revoke(sid)`；补单测断言"改密后 `/api/v1/me` 返回 401"；同一处顺手核对 `me/password.go` 的验证码重置路径（它已传 sid，确认是否也 revoke）。 |
| E2 | 🎯 | **一体化 compose 缺 dev 构建参数，US3 场景 2 必失败**：plan D7 只讲了 `API_UPSTREAM`。若不显式传 `--build-arg`，前端产物里 `VITE_ADMIN_HOME` 取「dev 缺省 `http://localhost:5174/`」、`VITE_PORTAL_LOGIN_URL` 取 `http://localhost:5173/login`，而一体化里后台在 `8090`、门户在 `8088` → 点「去后台」跳到空的 5174、会话失效跳 5173。 | 在 plan/data-model §3 增加「一体化 compose 的 build.args」一行：portal `VITE_ADMIN_HOME=http://localhost:8090/`；admin `VITE_PORTAL_LOGIN_URL=http://localhost:8088/login`、`VITE_PORTAL_HOME=http://localhost:8088/account/profile`；quickstart §1 加断言"点『去后台』落到 localhost:8090"。 |
| E3 | 🎯 | **探针会走全局限流**：`internal/api/router.go:45-47` 是 `r.Use(Recover) / r.Use(Trace) / r.Use(RateLimit(...))`，`RateLimit`（`middleware/ratelimit.go:20`）只对 `/docs/` 短路。于是 `/healthz`、`/readyz` 每次探活都消耗 `RATE_LIMIT_API_PER_MIN` 配额；一旦运维把配额调到个位数（或探活频率提高、多个 LB 共用一个出口 IP），探针开始 429 → 容器被判 unhealthy → 反复重启，故障自放大。 | `RateLimit` 增加对 `/healthz`、`/readyz` 的短路（与 `/docs/` 同一处，注明理由：探针不是业务请求、不能被配额化）；contracts/health-probes.md 增加条款与用例："把 `RATE_LIMIT_API_PER_MIN=1` 后连续请求 `/healthz` 仍 200"。 |
| E4 | 🎯 | **`COOKIE_DOMAIN` 在 `prod` 无非空/主域校验**：`internal/config/config.go:301-308` 只校验 issuer 为 https、`COOKIE_SECURE=true`。宪法「技术与接口约束」要求"必填项缺失必须非零退出"；而 host-only 正是 DEPLOYMENT §11 排障表里的第一条症状，说明它是最常见的配错项。plan 的 data-model §4 写了"prod 必须非空且为主域"，但文件清单没有对应的 `config.go` 校验与用例 → 计划与规格不一致。 | `validate()` 增加：`prod` 下 `CookieDomain` 非空且以 `.` 开头（且不含 `://`、不含尾斜杠）；`config_test.go` 补两条用例（空 / `sso.example.com`）；data-model §4 的"校验"列写明。 |
| E5 | 💡 | **nginx 启动期解析 upstream**：`proxy_pass http://api.<主域>;` 若是静态主机名，nginx 在**启动时**解析，DNS 或后端未就绪会导致 nginx 直接退出→ restart 循环（日志只在容器里，排障容易被误导成"配置错"）。 | 编排层用 `depends_on: {sso: {condition: service_healthy}}`（一体化）与 `restart: unless-stopped`（test/prod）；DEPLOYMENT §11 增加"前端容器反复重启 → 查 DNS/upstream 解析"一条；若要求 DNS 抖动也不影响启动，再考虑 `resolver` + 变量式 `proxy_pass`（本期可不做，但要写明取舍）。 |
| E6 | 💡 | **`envsubst` 陷阱未写进契约**：若实现时手写 `envsubst < tmpl > conf`，nginx 变量 `$host`、`$uri`、`$remote_addr` 会被替换成空串，产生**静默错误配置**（反代正常但日志/头全错）。官方 `20-envsubst-on-templates.sh` 只替换已定义的环境变量，必须用它。 | contracts/nginx-routing.md §5 增加一句硬约束："**禁止**裸 `envsubst`；只使用官方镜像的 `/etc/nginx/templates/*.template` 机制"，并在 review checklist 里列该项。 |

### 4c. Security & Privacy Review

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E7 | 💡 | **多跳 `X-Forwarded-For` 与 `TRUSTED_PROXIES` 的匹配关系没写清**：生产链路是 `浏览器 → 入口 LB → portal/admin nginx → api 入口 → sso:8081`，至少两跳。R2 的算法是"从右往左取第一个**不在可信列表**里的地址"，若 `TRUSTED_PROXIES` 只写入口 LB 网段而漏了前端容器网段，取到的就是**前端容器 IP**——审计 IP 全变成 `172.x`，且"看起来像配好了"。 | contracts/env-and-build.md §1.1 写明"必须列出**全部**反代网段（入口 LB + 前端容器网段 + api 入口）"；quickstart §4 增加反证："故意少配前端网段 → 审计 IP 变为容器网段"，把这个失败模式变成可自检项。 |

其余（密钥不入镜像、env 模板占位符、`/readyz` 不回传错误原文、`api` 域不配证书）在 plan/data-model 中已覆盖，无新增。
