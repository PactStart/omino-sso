# Feature Specification: 应用管理员标记与应用内管理入口

**Feature Branch**: `006-app-admin-role`

**Created**: 2026-10-22

**Status**: Draft

**Input**: User description: "应用成员表新增一个字段用于标记成员是否是应用的管理员。一个应用可以有多个管理员，在admin前端里可以管理员可以修改某个成员成为管理员还是普通用户。如果用户是应用的管理员，portal我的应用页面，应用的打开按钮左边需新增一个管理按钮，点击管理按钮，行为和admin端进入应用详情一样，应用管理员可以对应用成员、应用角色、应用权限进行操作，和现在admin完全一致，可以复制代码过去，portal端访问对应接口需要增加中间件，只有应用管理员才能做这些操作。"

## Clarifications

### Session 2026-10-22

- Q: 门户里的「管理」界面除了成员、角色、权限，是否也要能改应用的基础信息（名称、描述、Logo、回调地址）或密钥？ → A: 初版只做成员 / 角色 / 权限；基础信息与密钥仍只在 admin 端。
- Q: 点击「管理」后，门户里的应用管理界面以哪种形式打开？ → A: 独立页面（地址可收藏、刷新后仍停留在该应用的管理页）。

### Session 2026-10-22（口径调整）

- Q: 门户是否需要应用详情（基础信息）页？可编辑范围如何？ → A: 需要。门户新增「应用信息」页，**参考** admin 端应用详情（字段可展示），但**可编辑字段缩减为名称 / 描述 / Logo / 回调地址**；登出地址、两类令牌有效期、启用状态只读。admin 端保持原状（8 个可编辑字段）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 平台管理员授予或取消应用管理员 (Priority: P1)

企业 IT 管理员在 admin 端打开某个应用的成员列表，看到每位成员当前是「应用管理员」还是「普通成员」，并可随时切换。被设为管理员的成员从此可以在门户侧自行管理这个应用，不再需要 IT 介入日常维护。

**Why this priority**: 没有「把某人设为应用管理员」这一步，后续所有门户内管理能力都没有授权来源，是本特性的入口。

**Independent Test**: 只实现本条也能独立验收——在 admin 端把成员 A 设为管理员、把成员 B 保持普通成员，随后查看两人在门户「我的应用」页的差异（A 有管理入口，B 没有）。

**Acceptance Scenarios**:

1. **Given** 成员 A 是应用 X 的普通成员，**When** 平台管理员在 admin 端把 A 设为应用 X 的管理员，**Then** 成员列表中 A 显示为「应用管理员」，且刷新后状态保持。
2. **Given** 成员 A 是应用 X 的应用管理员，**When** 平台管理员取消其管理员身份，**Then** A 立即变回普通成员，门户侧不再出现管理入口。
3. **Given** 应用 X 已有 2 名应用管理员，**When** 平台管理员把第 3 名成员设为管理员，**Then** 操作成功，应用管理员数量不设上限。
4. **Given** 一次管理员身份变更已完成，**When** 查看审计记录，**Then** 能看到操作者、应用、目标成员、变更前后身份、时间与结果。

---

### User Story 2 - 应用管理员在门户看到并使用管理入口 (Priority: P1)

应用管理员登录门户，在「我的应用」里每个自己有管理权的应用卡片上，「打开」按钮左侧多出一个「管理」按钮。点击后进入该应用的管理界面，视觉与操作体验与 admin 端进入应用详情后一致。

**Why this priority**: 这是应用管理员感知到新能力的唯一入口，也是与「打开应用」这一既有行为并存的差异化入口。

**Independent Test**: 用应用管理员与普通成员两个账号分别登录门户，对比「我的应用」卡片上按钮的数量与点击结果。

**Acceptance Scenarios**:

1. **Given** 用户 U 是应用 X 的应用管理员，**When** U 打开门户「我的应用」，**Then** 应用 X 的卡片上同时出现「管理」与「打开」，且「管理」位于「打开」左侧。
2. **Given** 用户 U 只是应用 X 的普通成员，**When** U 打开门户「我的应用」，**Then** 应用 X 的卡片只有「打开」，没有「管理」。
3. **Given** 用户 U 是应用 X 与 Y 的管理员、应用 Z 的普通成员，**When** U 查看「我的应用」，**Then** 仅 X、Y 显示「管理」。
4. **Given** 用户 U 的管理员身份刚被取消且其页面仍停留在「我的应用」，**When** U 刷新页面，**Then**「管理」按钮消失，且直接访问管理界面的地址被拒绝。
5. **Given** 用户 U 是平台管理员但不是应用 X 的应用管理员，**When** U 查看门户「我的应用」，**Then** 应用 X 不显示「管理」入口（其平台能力只在 admin 端体现）。
6. **Given** 用户 U 收藏了应用 X 的管理页地址，**When** U 直接访问或刷新该地址，**Then** 有管理权限时直接进入该页并停留在应用 X，无权限时看到明确的「无权限」提示。

---

### User Story 3 - 应用管理员在门户完成日常管理 (Priority: P1)

应用管理员在门户的管理界面里维护自己应用的人员与权限：查看/搜索/添加/移除成员、创建与维护角色、创建与维护权限、把权限授予角色、把角色授予成员。所有操作与 admin 端完全一致，不需要再找 IT 到 admin 端代劳。

**Why this priority**: 这是本特性交付的实际价值；没有它，「管理」按钮只是空壳。

**Independent Test**: 仅以应用管理员身份（不登录 admin）在门户完成一轮「新增角色 → 给角色配权限 → 把角色授给成员 → 移除成员」，随后由平台管理员在 admin 端核对结果一致。

**Acceptance Scenarios**:

1. **Given** 应用管理员 U 进入应用 X 管理界面的成员页，**When** U 添加一名候选用户为成员，**Then** 该用户出现在成员列表，admin 端同一列表同步可见。
2. **Given** 应用管理员 U 在角色页新建角色 R 并为其勾选权限 P，**When** U 保存，**Then** 角色 R 显示权限 P；在 admin 端查看同一角色结果相同。
3. **Given** 应用管理员 U 把角色 R 授予成员 A，**When** 保存，**Then** 成员 A 的角色列表含 R，且 A 下次进入应用时权限按既有规则生效。
4. **Given** 应用管理员 U 在门户移除成员 B，**When** 确认，**Then** B 不再是成员、其该应用的角色绑定一并解除，且 B 若原本是管理员则同时失去管理员身份。
5. **Given** 平台管理员在 admin 端刚修改了应用 X 的数据，**When** 应用管理员 U 在门户刷新同一页面，**Then** 看到与 admin 端一致的最新结果。
6. **Given** 应用管理员 U 在门户管理界面，**When** U 寻找「把某成员设为应用管理员」的入口，**Then** 找不到该入口——授予与取消管理员只能在 admin 端由平台管理员完成；平台管理员在 admin 端完成变更后，U 在门户刷新即可看到成员身份变化。

---

### User Story 4 - 权限边界与即时生效 (Priority: P2)

非管理员无法通过任何方式进入或调用应用管理能力；管理员身份变更后立即生效；一个应用的管理权不会外溢到其他应用。

**Why this priority**: 门户把原本只在 admin 端存在的能力开放给了业务用户，边界一旦失效即为越权漏洞，必须有独立可验收的安全故事。

**Independent Test**: 用普通成员账号直接请求管理操作（绕过前端）、用应用 X 的管理员操作应用 Y 的数据，均应被拒绝且不产生任何数据变更。

**Acceptance Scenarios**:

1. **Given** 用户 U 是普通成员（前端已隐藏按钮），**When** U 直接发起任一应用管理操作，**Then** 被拒绝（无权限），且应用数据不发生任何变化。
2. **Given** 用户 U 是应用 X 的管理员、不是应用 Y 的成员，**When** U 对应用 Y 发起成员/角色/权限操作，**Then** 被拒绝，且响应不泄露应用 Y 是否存在。
3. **Given** 用户 U 未登录或会话已失效，**When** 发起应用管理操作，**Then** 被要求重新登录。
4. **Given** 用户 U 的账号被停用但仍持有管理员标记，**When** U 尝试进入管理界面，**Then** 无法登录或无法执行管理操作。
5. **Given** 用户 U 的管理员身份被取消，**When** U 立即用同一会话发起管理操作，**Then** 被拒绝（无需等待重新登录或缓存过期）。
6. **Given** 用户 U 是多个应用的管理员，**When** U 操作其中一个应用，**Then** 其权限范围严格限定在该应用内。
7. **Given** 用户 U 是平台管理员但不是应用 X 的应用管理员，**When** U 在门户发起应用 X 的管理操作，**Then** 被拒绝；同一操作在 admin 端仍可正常完成。

---

### Edge Cases

- **取消最后一名管理员**：允许取消。平台管理员始终可在 admin 端兜底；界面对「该应用将没有应用管理员」给出确认提示，但不阻止。
- **把非成员设为管理员**：拒绝，并提示需先将其加入成员。
- **应用管理员尝试自行任命他人或辞职**：门户不提供该能力，直接请求也被拒绝；如需新增或取消管理员，由平台管理员在 admin 端操作。
- **应用管理员修改只读配置（登出地址 / 两类 TTL / 启停）**：门户只读展示，提交也不会生效（服务端只接受名称 / 描述 / Logo / 回调地址）；这些配置仍只在 admin 端由平台管理员维护。
- **应用管理员尝试修改密钥**：门户不提供该能力，直接请求也被拒绝；密钥轮换仍只在 admin 端。
- **收藏的管理页地址在权限被撤销后再打开**：提示「无权限」并提供返回「我的应用」的入口，不得停留在空白页或反复加载。
- **管理员把自己移出应用**：允许，操作后立即失去该应用的管理权；若其为最后一名管理员，按上一条处理。
- **成员被移出后重新加入**：默认恢复为普通成员，不保留原管理员身份。
- **账号停用后重新启用**：管理员标记保留，重新启用后恢复管理能力。
- **多个管理员同时修改同一条数据**：与 admin 端既有并发策略保持一致（后者失败并提示刷新重试），不得出现静默覆盖。
- **应用被停用或删除**：其管理员不再看到管理入口，相关管理操作被拒绝。
- **平台管理员同时是某应用成员但不是其应用管理员**：门户不显示「管理」入口，门户侧接口也拒绝其调用；其平台管理员的全部能力仍在 admin 端，不受影响。如需在门户操作，须由平台管理员在 admin 端授予其该应用管理员身份。
- **管理员在另一浏览器仍停留在管理页**：权限被撤销后，其下一次操作即被拒绝（页面停留不构成豁免）。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 为每个应用成员记录「是否该应用的管理员」这一身份，一个应用可以有零到多个应用管理员。
- **FR-002**: 平台管理员 MUST 能在 admin 端的应用成员列表中查看每位成员当前的「应用管理员 / 普通成员」身份，并可将任一成员在两者之间切换；重复设置同一状态不得报错或产生重复记录。
- **FR-003**: 门户侧的应用成员/角色/权限管理操作 MUST 只允许「该应用的应用管理员」执行；平台管理员不因平台身份获得门户侧权限（其管理路径是 admin 端既有接口），但本人同时是该应用的应用管理员时按应用管理员处理。
- **FR-004**: 门户「我的应用」页 MUST 对应用管理员在其可管理应用的「打开」按钮左侧展示「管理」按钮；对普通成员不展示。
- **FR-005**: 点击「管理」MUST 进入该应用的管理界面，覆盖：应用信息（参考 admin 详情展示）、成员列表与搜索、添加成员、移除成员、候选成员查询、角色增删改查、权限增删改查、角色与权限的绑定、角色与成员的绑定。应用信息中**只有名称、描述、Logo、回调地址可编辑**，登出地址、两类令牌有效期与启用状态只读；**密钥管理**与「设为/取消应用管理员」仍只在 admin 端提供（口径调整见 Clarifications 2026-10-22）。
- **FR-006**: 门户与 admin 端对**成员、角色、权限**的管理操作 MUST 使用相同的校验规则与错误提示；同一操作在两端的界面结果必须一致，不得出现「admin 能改、门户不能改」或反之。
- **FR-007**: 应用管理员身份的授予与取消 MUST 仅在 admin 端提供（由平台管理员执行）；门户管理界面 MUST NOT 提供该入口，应用管理员不能自行任命或撤销其他管理员（含自身）。
- **FR-008**: 成员被移出应用时 MUST 同时失去该应用的管理员身份；重新加入时默认是普通成员。
- **FR-009**: 账号处于停用状态时 MUST 不能执行任何应用管理操作；标记本身保留，重新启用后恢复。
- **FR-010**: 应用管理员权限 MUST 严格按应用隔离：对未担任管理员的其它应用不得有任何管理权限，尝试操作时被拒绝且响应不泄露该应用是否存在。
- **FR-011**: 管理员身份的新增、取消 MUST 立即生效，无需重新登录、无需等待缓存或令牌过期；其下一次请求即按新身份判定。
- **FR-012**: 管理能力 MUST 由服务端强制校验，前端隐藏按钮不得作为唯一防护；绕过界面的直接请求同样被拒绝。
- **FR-013**: 平台管理员 MUST 保留对全部应用的既有管理能力，本特性不得收回或改变其行为。
- **FR-014**: 管理员身份变更 MUST 写入审计记录，至少包含操作者、应用、目标成员、变更前后身份、时间与结果；门户侧的管理操作审计口径与 admin 端一致。
- **FR-015**: 应用被停用或删除后，其应用管理员 MUST 不再获得管理入口，且相关管理操作被拒绝。
- **FR-016**: 门户管理界面 MUST 是带独立地址的页面：地址可收藏、刷新后仍停留在该应用的管理页；直接访问该地址时，有权限则进入，无权限则给出明确的「无权限」提示而非空白页或永久加载。

### Key Entities *(include if feature involves data)*

- **应用成员**：用户与应用的成员关系，新增属性「是否为该应用的管理员」；同一用户在同一应用只有一条成员关系。
- **应用**：可被管理的目标对象，拥有成员、角色、权限；存在启用/停用状态。
- **应用角色**：应用内自定义角色，可绑定权限与成员。
- **应用权限**：应用内权限点，可被角色引用，支持层级。
- **账号**：门户用户，存在启用/停用状态，可同时是多个应用的成员与管理员。
- **审计记录**：记录管理员身份变更与门户内管理操作，字段与既有 admin 端记录一致。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 平台管理员把一个已有成员设为应用管理员，从打开成员列表到保存完成不超过 30 秒（3 次点击以内）。
- **SC-002**: 应用管理员在门户从登录到完成一次「新建角色并授予一名成员」不超过 2 分钟，且全程无需访问 admin 端。
- **SC-003**: 非管理员（普通成员、未登录、已撤销管理员）对应用管理操作的尝试 100% 被拒绝，且审计中不产生任何被误认为成功的记录。
- **SC-004**: 门户与 admin 端对同一操作的结果一致率 100%（同一输入得到同一结果与同一错误提示）。
- **SC-005**: 管理员身份变更后，对应用户的入口可见性与操作权限在**下一次请求**即完成切换（0 次重新登录、0 个旧权限残留）。
- **SC-006**: 管理员身份变更 100% 可追溯到「谁在什么时间把谁设/取消成了哪个应用的管理员」。

## Assumptions

- **A1 仅 admin 端授予管理员**（2026-10-22 确认）：应用管理员身份的授予与取消只在 admin 端由平台管理员执行；门户管理界面不提供该入口。门户内的成员/角色/权限管理能力仍与 admin 端一致。
- **A2 门户授权只认应用管理员**（2026-10-22 确认）：门户管理入口与接口只对「该应用的应用管理员」开放；平台管理员的管理路径为 admin 端，不因平台身份获得门户侧权限。两者身份重叠时（同一个人既是平台管理员又是该应用管理员），门户按应用管理员处理。
- **A3 不强制保留管理员**（2026-10-22 确认）：允许取消最后一名应用管理员，仅做界面确认提示；平台管理员可随时补位。
- **A4 标记随成员关系存在**：管理员标记依附于成员关系，不单独存在；成员关系解除即失效。
- **A5 停用语义**：账号停用期间保留标记但不可用，重新启用后自动恢复，不要求重新授予。
- **A6 审计沿用既有模型**：不新增独立审计体系，复用现有审计事件与字段口径（必要时扩展事件类型）。
- **A7 单一实现来源**：既有 admin 端成员/角色/权限的业务规则与校验是唯一事实源，门户侧复用同一规则，而不是各自实现一份（避免两端漂移）。
- **A8 范围边界**：门户管理页覆盖应用信息（2026-10-22 口径调整：名称 / 描述 / Logo / 回调地址可编辑，登出地址 / TTL / 启停只读）与成员 / 角色 / 权限 / 授权；**不含密钥**与「设为/取消应用管理员」。不改变应用层面（平台级）的授权模型，不涉及 SSO 登录流程、令牌签发与 scope 语义；移动端与开放 API 不在本期范围。
- **A9 管理员规模**：单个应用的管理员数量不设上限，也不设最少人数（除 A3 的提示外）。
