**Date**: 2026-11-04 00:00:57

**Plan**: [plan.md](../plan.md)
**Verdict**: ⚠️ PROCEED WITH UPDATES

## Executive Summary

这是一份**准备度较高**的规格与计划：需求的验收场景可判定、plan 把六个真正有争议的技术点（响应分工、批量写入、并发串行化、深度冲突、审计粒度、导出口径）都提前定死了，并且明确引用了既有代码位置。调研扎实——`ensureParent` 的查询放大、`audit.go` 的丢弃式队列、`LIMIT 1000` 的截断风险都被找出来了。

但有两处**必须落地前修正**的硬伤：① **plan 的审计口径与 spec 直接冲突**——SC-003 与 US3 的独立测试明确要求"全量 no-op 的重复导入不产生新的成功事件"，而 plan/R7 写的是"成功导入恒写 1 条"；照 plan 实现会让 SC-003 与 US3 的验收直接失败。② **导出与导入的上限不对称且未闭环**——导出若复用既有 `LIMIT 1000` 的列表查询会**静默截断**（数据丢失且无提示），而"导出→回导"正是 US4 的全部价值；再加上导入侧的 1000 条 / 256KB / 10 层三个上限，使"跨环境搬运"这一产品承诺在边界数据上必然破裂。

产品侧的主要短板是**首次使用门槛**：`SC-001` 只度量"导入时 ≤3 次操作"，完全不计"准备这份 1000 条 JSON"的成本——而 spec 刻意不提供代码编辑器、不提供模板，管理员第一份文件从零手写。这不是阻断项，但会让特性只在"已有 JSON 的人"之间流转。

结论：**修 2 个 Must-Address + 采纳 6 条建议即可进入 `/speckit.tasks`**，不需要回到 specify/plan。

## Product Lens Findings 🎯

### Problem Validation

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| P1 | 💡 | **"准备内容"的成本没有被任何成功标准覆盖。** SC-001 度量的是"粘贴/选文件 → 校验 → 确认"三次操作，但真实瓶颈在之前：管理员要从零写出 1000 条嵌套 JSON。US4（导出）只解决"从别处搬"，不解决"第一个应用第一次导入"。spec 也刻意排除了代码编辑器类依赖，导致首次使用者只有"自己手写"一条路。 | 在导入对话框给一个**"下载示例"**入口（静态 JSON 文本，5 条三层，含 `version`/`mode`/`children`/`sort` 的写法）。零依赖、约 20 行，能把"从零写"变成"改一个现成的"。同时在 SC-001 旁补一句口径说明："本指标不含内容准备成本"。 |
| P2 | 🤔 | **两层含义的"层级上限"共存，产品承诺有例外。** spec FR-012 定 10 层，既有单条创建用的是 `maxPermissionDepth=100` 的父链护栏（`internal/service/app_auth.go:63`）。plan 选择"两者并存 + 导出不裁剪"，结果是：库里若存在 >10 层的树，**导出成功但回导必失败**——而 US4 的产品承诺正是"导出后再导入到另一环境"。 | 需裁决（不可由团队单方面定）：① 接受该例外并在 UI 明示（plan 现方案）；② 把导入深度上限提到与既有护栏一致（`maxPermissionDepth`），从此无例外；③ 保持 10 层，但导出时若超深则**拒绝导出**并提示"请先整理层级"。建议选 ② —— 三层是真实用法，10 层对权限字典没有产品意义，为它牺牲闭环不值得。 |

## Engineering Lens Findings 🔬

### Architecture Soundness

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E1 | 🎯 | **审计口径与 spec 直接冲突（Constitution「改动必须伴随测试」+ SC-003 双重违背）。** plan 的 R7 与 `contracts/admin-permission-import.md` §2 写"成功导入恒写 1 条聚合事件"。但 spec **SC-003** 要求"第二次的新增数与更新数均为 0、无变化数等于输入条数，**且不产生新的成功审计事件**"；**US3 的 Independent Test** 也明确"审计日志没有新增记录"。照 plan 实现，这两条验收必失败。反证：010 的既有写法正是"`unchanged` 跳过、不产生事件"（`internal/api/admin/org_grant.go:106-108`）。 | 改为：**仅当 `added > 0 || updated > 0` 时写 1 条成功事件**；全 no-op 不写（与 010 惯例一致）。同步修 3 处：plan「实施要点·审计 1 条兜底」、`research.md` R7、`contracts/admin-permission-import.md` §2；并在集成测试里固定断言"连续两次导入 → 审计仅 1 条"。 |
| E2 | 💡 | **新增 handler 继续加厚 `internal/api/admin/app_auth.go`**（实测 **1049 行**，已承载成员/角色/权限/授权四类逻辑），再加 3 个 handler + 一个错误映射函数，会突破 1200 行。 | 新建 `internal/api/admin/app_permission_import.go`，只放 3 个 handler + `failPermissionImport`；`app_auth.go` 零改动。service 侧已经是新文件，两侧对齐更好定位。 |

### Failure Mode Analysis

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E3 | 💡 | **审计写入是"队列满即丢"（`internal/service/audit.go:111-115`）。** 导入恰恰是全系统"写入放大"最大的操作（一次 1000 条），也是事后追责最需要留痕的操作，却与普通事件共用同一个会丢弃的通道。queue full 时只有一条 `Warn`。 | 二选一并写进 plan：① 接受该风险，但把 `Warn` 升级为带 `event_type=app_permissions_imported` 的**结构化错误日志**（便于 grep 出"这次导入丢了审计"）；② 导入事件走同步落库（同事务内写 `audit_events`，代价是事务多一次写）。建议 ①，成本最低且可观测。 |
| E4 | 💡 | **导入期间的单条并发编辑会被 JSON 静默覆盖。** 事务内 `FOR UPDATE` 读到的是最新提交数据，因此不会写坏；但"管理员 A 正在导入、管理员 B 同时改了某权限点的名称"时，B 的修改会被 A 的 JSON 覆盖（因为嵌套结构是权威）。这符合 FR-016 的语义，但没人告诉 B。 | 在 plan 的「实施要点」里显式写明该行为（"导入以文档为准，导入期间的并发单条编辑可能被覆盖"），并在契约的 `409 APP_RESOURCE_STALE` 说明里补一句"仅唯一键冲突时返回，语义覆盖不算冲突"。避免实现者自作聪明地加逐条乐观锁（那会让 1000 条导入因一条被改而整批失败）。 |
| E5 | 💡 | **没有端点级限流。** 导入是"1000 条 × 单事务"，反复提交可对 DB 造成持续压力；现有 `RateLimit` 是全局中间件（`internal/api/middleware/ratelimit.go`），阈值面向普通请求。 | 至少在 plan 记录该风险与观察方式（导入 p95 + `APP_PERMISSION_IMPORT_*` 触发率）；若实测有滥用，再为导入加独立令牌桶（新增 env → §9 三向同步）。**不建议**本期引入（避免三处注册表联动）。 |

### Security & Privacy

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E6 | 💡 | **`X-Import-Source` 可被任意伪造，却被用于审计字段。** 本身无安全事故（只是来源标记），但若不写明"不可信"，后续可能有人拿它做安全判断。 | 在契约 §1 与 AGENTS §6.7 的事件说明里标注"`source` 由客户端声明，仅供统计，不得作为安全依据"。 |
| E7 | 💡 | **超深 JSON 的解析防护没写。** 若有人提交 10000 层嵌套，递归解析有爆栈风险（`encoding/json` 内部有 `maxNestingDepth=10000` 会报错，但没人确认过路径）。 | 在 plan 的失败模式里加一句：解析用 `encoding/json` 的深度上限兜底，且**解析后立刻做 10 层检查**（`too_deep`），不自己写递归下降解析器。 |

### Performance & Scalability

| ID | Severity | Finding | Suggestion |
|----|----------|---------|------------|
| E8 | 💡 | **256KB 与"1000 条满字段"不自洽，且 FR-013 的措辞对体积超限不成立。** 最坏情况：`code` 64 + `name` 64 + `description` 255 ≈ 430 字节/条 × 1000 ≈ **430KB > 256KB**——条数上限可达但体积先撞墙。更麻烦的是 spec FR-013 要求"提示中包含实际上限值与**本次实际条数**"，而体积超限时 body 根本读不完整，**无法给出条数**。 | 两处一起修：① `maxImportBodyBytes` 提到 **512KB**（覆盖 1000 条满字段），让两个上限不再互相打架；② 把 FR-013 措辞改为"条数超限时提示条数与上限；体积超限时提示体积与上限"，避免要求实现一件做不到的事。 |
| E9 | 💡 | **逐条 `Updates` 的 1000 次往返未给"升级路径"的触发条件。** plan 只说"可接受、预留优化"，但没给判据。 | 补一句判据：若 SC-005 实测 p95 > 5s，按"相同字段组合"分组批量 `WHERE id IN (...)` 更新（不改变计数口径）。这是实现期可判定的门限，不是"以后再说"。 |

## Cross-Lens Insights 🔗

| ID | Finding | Product Impact | Engineering Impact | Suggestion |
|----|---------|---------------|-------------------|------------|
| X1 | **"导出 → 回导"这三个字有四个隐含上限，其中两个目前会静默失败。** 导出侧若复用 `ListClientPermissions`（`internal/store/app_auth_store.go:527-532`，`LIMIT 1000`）会**静默截断**；即便不截断，>1000 条或 >256KB 或 >10 层的导出文件**回导必被拒**。US4 的产品承诺（"带到测试环境或另一个应用上导入"）在边界数据上没有兑现路径，而管理员不会知道。 | US4/SC-004 的承诺是"100% 一致"，但边界数据上会得到"少了一部分"或"导入被拒"且无事前告知——这是信任损失最大的一类缺陷（静默丢数据）。 | 需要新增一个**无 LIMIT** 的导出查询（顺带去掉 `child_count`/`role_count` 两个相关子查询，更快），并让导出响应显式给出"这份文件能不能回导"。 | ① 导出改用独立查询 `ListClientPermissionsForExport`（无 `LIMIT`、无计数子查询）；② 导出响应把 `maxDepth` 升级为 `importable: {ok, reasons[]}`，`reasons ∈ {too_many, too_large, too_deep}`；③ 前端在 `ok=false` 时于下载前提示"该应用权限过多/过深，导出文件可用于备份，但无法回导"。一个字段同时覆盖条数、体积、深度三个不对称。 |
| X2 | **"预览 → 确认"是纯前端纪律（无票据），而两个上限都会在确认时才暴露。** 预览通过后未确认，稍后点了确认却 413 / 409——管理员会认为"预览骗了我"。 | 需要一句可解释的偏差提示，否则会被当成 bug 报上来。 | 无票据是对的（plan 已论证），但需要前端把 `409/413` 的文案与"重新校验"按钮绑在一起，而不是弹一个通用错误。 | 契约 §2 的"前端处置建议"列补：`413 → 提示裁剪并给"重新校验"按钮`；`409 → 提示"数据已被更新，已为你重新校验"并自动重跑一次预览`（成本一行）。 |
