# Feature Specification: 应用权限点批量导入

**Feature Branch**: `011-app-permission-import`

**Created**: 2026-11-03

**Status**: Draft

**Input**: User description: "应用权限点一般都很多，一个个手动添加太麻烦了，需要批量导入的功能，比如上传一个 json 文件或者 json 编辑器填写一个 json，提交就能导入。json schema 校验 json 格式，json 支持层级，比如 children 字段"

## Clarifications

### Session 2026-11-03

- Q: 如果一份导入的 JSON 把一个已经存在的权限点放到了另一个父节点下面，系统应该按 JSON 改写它的父级，还是拒绝这次导入？ → A: 按 JSON 改写父级；预览结果中单列"N 条权限点的上级将变更"，管理员确认后才写入。（嵌套结构即唯一权威，改写才能让导出→导入闭环；把变更条数暴露在预览里使风险可预期。）
- Q: 单次最多 1000 条这个数字，是限制"一次提交的条数"，还是限制"一个应用最多能有这么多权限点"？ → A: 只是单次提交上限；应用权限点总量不新增限制，沿用现状。（避免把已有一千多条权限点的大应用卡死，也不在本特性里引入新的全局配额。）
- Q: 点"校验"但校验没通过时，要不要在审计日志里留一条失败记录？ → A: 不写。校验预览是只读动作，不产生任何审计记录；只有"确认导入"的失败与成功各写 1 条。（校验是高频试探动作，逐次留痕会把审计页淹没；有后果的是确认导入，它的成败才需可追溯。）
- Q: 导入文件里要不要接受 `version` 和 `mode` 这类元字段，还是把除 `permissions` 之外的一切字段都当作未知字段拒掉？ → A: 接受并校验：`version` 仅支持 `1`、`mode` 仅支持 `merge`，其它值明确拒绝（`replace` 提示"暂不支持全量对齐"）；其余未知字段一律拒绝；导出时写入这两个字段。（留出版本位与模式位便于后续扩展，同时保证"自家导出文件能原样回导"。）
- Q: 导入失败时对外返回几个错误码——是全部归成一个"导入内容不合法"，还是把"内容有问题"和"内容太多"分开？ → A: 两个码。`APP_PERMISSION_IMPORT_INVALID` 覆盖结构/字段/编码/重复/超深/超长；`APP_PERMISSION_IMPORT_TOO_LARGE` 覆盖条数与体积超限。（"改内容再试"与"裁剪后再试"是两种修法，必须让前端能分辨。）

### Session 2026-11-04

- Q: 导入的层级上限取 10 层（独立于单条创建），还是沿用既有单条创建的 100 层？ → A: 沿用 100 层。两层上限并存会让库里 >10 层的历史树"能导出、导不回"，而"导出→回导"正是本特性的核心承诺（US4）；三层是真实用法，10 层对权限字典没有产品意义，不值得为它制造闭环例外。
- Q: 重复导入一份完全无变化的文档，要不要再写一条成功审计事件？ → A: 不写。新增与更新都为 0 时视为"无后果动作"，与校验预览同等对待（spec SC-003 与 US3 的独立测试本就要求"审计无新增"）；这也与既有组织授权的"幂等提交不产生事件"一致。
- Q: "内容非法"导致的确认导入失败，要不要写失败审计事件？ → A: 不写。失败事件只覆盖"业务拒绝"（并发冲突、条数/体积超限、应用不可用）；语法错误、字段非法这类"改内容再试"与预览失败同为无后果动作，若逐次留痕会把审计页淹没（与既有"输入格式错误不记"口径一致）。
- Q: 导出的文件如果不满足导入上限（条数/体积/深度），还要不要允许导出？ → A: 允许，但必须显式判定"这份文件能否回导"。导出是备份与人工参考的正当用途，直接拒绝会剥夺该价值；静默产出一份导不回去的文件则是最坏结果。
- Q: "能否回导"的判定按哪种序列化算体积——紧凑的，还是下载文件那种带缩进的？ → A: 必须与下载文件的实际字节一致（按格式化后的序列化结果算）。紧凑序列化在 3 层嵌套下比实际文件小 20%–30%，按它判定会出现"说能回导、下载后被拒"的假承诺，比不提供该判定更糟；同时空权限点也必须判为"不可回导"。
- Q: 误导入了一批权限点，事后怎么处置？ → A: v1 不做"撤销导入"，但审计必须留下可处置的线索：记本次新增的权限点标识（前 20 个 + 总数）与导入文档哈希。这样"误导入 1000 条"至少能用一条 SQL 按标识清理，且能确认当时导入的是哪份文件，不必为此新建"批次"实体。
- Q: 导入来源（粘贴/文件）用请求头还是查询参数传？ → A: 查询参数（`?source=paste|file`），非法值一律按"粘贴"处理。自定义头在前后端分域部署时会触发 CORS 预检（管理面未挂 CORS），且非法取值行为需要额外定义；查询参数两者都不涉及。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 一份 JSON 一次性导入大量权限点 (Priority: P1)

平台管理员在应用的权限管理页，不再逐个点"新建权限"填编码和名称，而是把整份权限点清单（几十到上千条）粘贴进一个文本框，或者直接选一个本地 `.json` 文件；系统先校验并告诉他"将新增 132 条、更新 3 条、无变化 5 条"，确认后一次性写入，权限树立刻成型。

**Why this priority**：这是本特性的全部价值。现状是单条创建，一个中大型应用（订单、营销、结算）动辄上百个权限点，逐个填表既慢又容易写错编码；没有这条链路，后面的层级、导出、审计都没有意义。

**Independent Test**：在一个空权限的应用里，粘贴一份含 50 条权限点的 JSON，点"校验"看到"将新增 50 条"，点"确认导入"后权限列表出现全部 50 条，编码与名称逐条与输入一致；全程只填过一次编码和名称（在 JSON 里）。

**Acceptance Scenarios**：

1. **Given** 应用 P 尚无任何权限点，**When** 管理员粘贴一份 50 条权限点的合法 JSON 并点"校验"，**Then** 返回"将新增 50 条、更新 0 条、无变化 0 条"，且此时权限列表仍为空（未写入任何数据）。
2. **Given** 已完成上述校验，**When** 管理员点"确认导入"，**Then** 50 条权限点全部出现，编码、名称、描述、排序与输入一致，并提示成功条数。
3. **Given** 管理员选择本地 `.json` 文件而不是粘贴，**When** 导入同一份内容，**Then** 结果与粘贴完全一致（同一路径、同一校验、同一结果）。
4. **Given** 一份 JSON 中有一条权限点的编码含非法字符，**When** 点"校验"，**Then** 明确指出"第 3 条（`permissions[2].code`）编码含非法字符，只允许字母、数字与 `_.:-`"，且不写入任何数据。
5. **Given** 校验未通过，**When** 管理员按提示改好输入再点"校验"，**Then** 之前的错误清单被本次结果替换，不残留旧错误。
6. **Given** 输入为空或不是合法 JSON，**When** 点"校验"，**Then** 提示"内容不是合法的 JSON / 内容为空"，且不发起任何写入。

### User Story 2 - 层级用嵌套表达，导入后直接成树 (Priority: P1)

权限点的层级（域 → 模块 → 动作）在 JSON 里用 `children` 直接嵌套表达，管理员不用去查每个权限点的内部标识再手工指定父级；导入完成后权限树按输入的结构展开，父子关系正确，层级过深或结构自相矛盾时在校验阶段就被拦下。

**Why this priority**：权限点的价值一半在层级——平铺的几百条编码无法阅读，也就无法授予角色。若只支持平铺，等于把"逐个新建"换成"逐个新建但不用点鼠标"，仍要人工建父子关系，问题没解决。

**Independent Test**：导入一份三层嵌套的 JSON（`order` → `order.write` → `order.write.refund`，共 3 条），确认权限树展开为三层且父子关系正确；再构造一份嵌套 101 层（超过既有 100 层上限）的 JSON，确认校验阶段即被拒绝并指出超限节点。

**Acceptance Scenarios**：

1. **Given** 一份三层嵌套、共 12 条权限点的 JSON，**When** 确认导入，**Then** 权限树呈现为三层，每个子节点的父级是其在嵌套中对应的上层节点。
2. **Given** 同一份 JSON 里"子节点排在父节点之前"（数组顺序与层级无关），**When** 导入，**Then** 父子关系仍正确（父级先落库，与数组顺序无关）。
3. **Given** 一份嵌套 101 层、超过层级上限（沿用既有 100 层）的 JSON，**When** 点"校验"，**Then** 明确指出"第 N 条路径深度 101 超过上限 100"，且不写入任何数据。
4. **Given** 同一份 JSON 中两个不同父节点下出现相同编码，**When** 点"校验"，**Then** 报"编码重复"，并同时给出两处位置。
5. **Given** 某条编码没有以父级编码为前缀（如父 `order`、子 `pay.refund`），**When** 点"校验"，**Then** 仅给出提示（不阻断），管理员可继续导入。
6. **Given** 省略 `sort`，**When** 导入成功，**Then** 同一层级内的展示顺序与 JSON 中的书写顺序一致。
7. **Given** 应用 P 已有 `order.read` 挂在 `order` 之下，**When** 导入的 JSON 把 `order.read` 放进 `pay` 的 `children`，**Then** 校验预览显示"1 条权限点的上级将变更"，确认导入后 `order.read` 的上级变为 `pay`，其既有角色绑定不受影响。
8. **Given** 导入会把某节点移到其原有后代节点之下（`A → B` 改为 `B → A`），**When** 导入，**Then** 父子关系按输入整体重写且不形成环（`B` 变为根级、`A` 挂到 `B` 之下）。

### User Story 3 - 重复导入不产生重复数据 (Priority: P2)

同一份 JSON 反复导入（比如改了几个名称后重新提交，或者两个人先后导入），系统按编码识别"已经存在的那些"，只更新有变化的字段，其余标记为"无变化"；不会出现同名重复权限点，也不会把已有权限点删除。

**Why this priority**：批量导入天然会被重复执行（改一处重传整份最多见）。若不能幂等，管理员每改一个名称就要手工挑出那一条来改，或者被迫先删后建——后者会连带解除已有的角色绑定，风险高。

**Independent Test**：导入一份 20 条的 JSON 后，原样再导入一次，确认"新增 0、更新 0、无变化 20"，权限点数仍是 20，且审计日志没有新增记录。

**Acceptance Scenarios**：

1. **Given** 应用 P 已有 20 条权限点，**When** 原样再导入同一份 JSON，**Then** 结果为"新增 0、更新 0、无变化 20"，权限点数量不变。
2. **Given** 管理员改了其中 3 条的显示名称后重新导入，**When** 确认导入，**Then** 结果为"新增 0、更新 3、无变化 17"，只有那 3 条的名称变化。
3. **Given** 应用 P 已有权限点 `order.export`，**When** 导入的 JSON 里没有它，**Then** 该权限点仍存在，未被删除。
4. **Given** 导入更新了某条权限点的名称，**When** 查看已引用该权限点的角色，**Then** 绑定关系不变（角色仍持有该权限点）。
5. **Given** 两名管理员几乎同时导入同一份 JSON，**When** 两者都提交，**Then** 不出现重复权限点或半成品层级；其中一方若因冲突失败，得到"请刷新后重试"的明确提示。

### User Story 4 - 导出后再导入，跨环境搬运 (Priority: P2)

管理员能把应用现有的权限点一键导出成与导入完全同构的 JSON，带到测试环境或另一个应用上导入，编码与层级一致；这样"搬权限点"不必手工重敲，也让第一份 JSON 有了现成的起点。

**Why this priority**：批量导入的真实使用场景里，"从别处搬一份过来"占多数。没有导出，管理员第一份 JSON 就得从零手写，导入的收益被打折；而导出成本极低、风险也低。

**Independent Test**：从应用 A 导出权限点到文件，在应用 B（空权限）导入该文件，确认 B 的权限点数量、编码、层级与 A 完全一致。

**Acceptance Scenarios**：

1. **Given** 应用 A 有 3 层共 30 条权限点，**When** 管理员点"导出"，**Then** 下载到一份 JSON，结构为嵌套 `children`，不含任何内部标识（不使用权限点 ID 或父级 ID 作为引用）。
2. **Given** 已导出 A 的 JSON，**When** 在空权限的应用 B 导入，**Then** B 得到 30 条权限点，层级与 A 一致，编码逐条相同。
3. **Given** 应用 A 的权限点含特殊字符编码（如 `order.item:read`），**When** 导出后再导入，**Then** 编码原样保留，不被转义或截断。

### User Story 5 - 门户应用管理员具备同等能力 (Priority: P2)

被设为应用管理员的业务同事，在门户的应用管理里也能对该应用做权限点批量导入与导出，结果与平台管理员在 admin 端完全一致，不必把整份清单发回给 IT 代劳。

**Why this priority**：权限点属于业务语义（"订单能不能退款"），业务侧最清楚该怎么分。既有的成员、角色、权限点单条维护都已经下放到门户应用管理员，批量能力若只在 admin 端，等于把刚拆掉的瓶颈装回去。

**Independent Test**：以应用管理员身份登录门户，为应用 P 导入 20 条权限点，然后在 admin 端用平台管理员打开同一应用，确认权限点与层级一致；再用另一位非该应用管理员的用户尝试同一操作，确认被拒绝。

**Acceptance Scenarios**：

1. **Given** 用户 U 是应用 P 的应用管理员（非平台管理员），**When** U 在门户导入 20 条权限点，**Then** 导入成功，admin 端同一应用立即可见这 20 条。
2. **Given** 用户 U 是应用 P 的应用管理员但不是平台管理员，**When** U 尝试为应用 Q 导入权限点，**Then** 请求被拒绝（原因不泄露 Q 是否存在）。
3. **Given** 同一份 JSON，**When** 分别在 admin 端与门户端校验，**Then** 结论一致（都通过，或给出同一组位置与原因）。
4. **Given** 应用 P 已被停用，**When** U 在门户打开权限页尝试导入，**Then** 导入被拒绝并给出与既有应用管理端点一致的原因说明。

### User Story 6 - 批量导入可追溯 (Priority: P3)

安全与运维在审计日志里能看到"谁在什么时候为哪个应用导入了权限点、新增/更新各多少条、是粘贴还是上传文件、成功还是失败原因"，用于回答"这几百个权限点是谁一次性加进来的"。

**Why this priority**：批量操作是放大面最大的动作，一次可能新增上千条权限点；没有可追溯的记录，出问题只能靠猜。它不阻塞主流程，但属于上线前要闭环的安全要求。

**Independent Test**：对应用 P 做一次成功导入与一次校验失败，在审计页按导入事件筛选，各出现 1 条记录，含新增/更新/无变化条数、来源与操作者；失败记录中能看出失败原因分类。

**Acceptance Scenarios**：

1. **Given** 管理员导入了 30 条（新增 28、更新 2），**When** 查询审计日志，**Then** 出现 1 条导入事件，含上述计数、来源（粘贴/文件）、操作者与时间。
2. **Given** 一次确认导入因并发冲突而失败，**When** 查询审计日志，**Then** 出现 1 条失败事件，含失败原因分类与操作者，且不出现任何"新增成功"的记录。
3. **Given** 一次导入包含 1000 条权限点，**When** 查询审计日志，**Then** 只出现 1 条聚合导入事件，不出现 1000 条逐条记录。
4. **Given** 管理员连续点 5 次"校验"且都没通过（未执行确认导入），**When** 查询审计日志，**Then** 不出现任何与导入相关的记录。

### Edge Cases

- **空输入**：内容为空、仅有空白、或 `permissions` 为空数组时 MUST 在校验阶段拒绝并提示"没有可导入的权限点"，MUST NOT 当作"成功导入 0 条"。
- **语法错误**：JSON 不合法时 MUST 提示"内容不是合法的 JSON"并尽量给出出错的行号/位置，MUST NOT 提交到服务端做语义校验。
- **未知字段**：`version`、`mode`、`permissions` 是约定字段（校验规则见 FR-006）；出现其它字段（如 `id`、`parentId`、`permissionList`）时 MUST 拒绝并指出字段名，避免用户误以为自己写的父级引用生效了。`version` 非 `1` 或 `mode` 非 `merge` 时 MUST 分别给出"仅支持版本 1"与"暂不支持全量对齐"的明确说明，MUST NOT 报成笼统的格式错误。
- **同批编码重复**：同一份输入内跨层级出现相同编码时 MUST 拒绝；两处位置都要指出，只报第一处会让用户改完再撞。
- **与库内编码冲突但内容相同**：视为"无变化"，不报错；与库内冲突且内容不同时视为"更新"，不报错——这是幂等的核心，报错会让"改一处重传整份"无法使用。
- **大小写差异**：编码 `order.read` 与 `Order.Read` 视为两个不同权限点（既有编码规则区分大小写）；校验时 MUST 给出"疑似重复（忽略大小写后相同）"的提示，但 MUST NOT 阻断。
- **移动节点时其原有子节点**：某权限点的上级被输入改写时，其原有子节点（未出现在本次输入中的）MUST 继续挂在它下面，MUST NOT 被顺带移动或删除；导入只改写输入中出现过的节点的父级。
- **超量**：单次超过 1000 条或请求体积超过上限（512KB）时 MUST 拒绝并提示上限值。**条数超限**的提示 MUST 含本次实际条数；**体积超限**时请求体无法完整解析，MUST NOT 声称知道条数，须给出实际上限并提示"可能是描述或名称过长所致"。
- **超深**：层级超过上限（沿用既有 100 层）时 MUST 拒绝并指出超限节点的路径与实际深度。
- **超长文本**：名称、描述超出既有长度上限时 MUST 拒绝并指出具体字段与最大长度；编码超长同理。
- **并发导入**：两个管理员同时导入时 MUST NOT 产生重复权限点或半成品层级；失败方的提示 MUST 是"请刷新后重试"，而不是内部错误。
- **应用状态异常**：应用不存在或被停用时导入 MUST 被拒绝；门户侧 MUST NOT 因为应用存在与否而泄露信息（与既有端点一致）。
- **导入过程中应用被删除**：整批失败并回滚，MUST NOT 留下部分权限点。
- **前端自行判定语义**：前端 MUST 只做"是否为空/是否为合法 JSON"的基础检查；编码规则、层级、重复等语义结论 MUST 以服务端返回为准，避免两端判定不一致。
- **失败后的输入保留**：校验或导入失败后，MUST 保留管理员已输入的内容（不清空编辑器），便于就地修改后重新校验。
- **权限点字典很大**：单应用上千条权限点属于正常规模，页面 MUST 仍可正常加载与展示；这类应用再次导入时 MUST 按"本次提交条数"校验上限，MUST NOT 因总量已超 1000 而拒绝。字典规模与"某个用户被授予上千条权限点导致令牌变大"是两件不同的事，前者不设限，后者沿用既有绑定上限。

## Requirements *(mandatory)*

### Functional Requirements

**入口与流程**

- **FR-001**: 应用权限管理 MUST 提供"批量导入"入口，支持两种输入方式：直接粘贴 JSON 文本、选择本地 `.json` 文件；两种方式 MUST 走同一条处理路径与同一套校验规则。入口 MUST 同时提供可下载的示例文档（至少 3 层，含 `version`、`mode`、`children`、`sort` 的写法），使首次使用无需从零手写；示例文档 MUST 附字段对照说明，含一份"表格行 → 嵌套 JSON"的三行对照（用 `a` 与 `a.b` 编码展示层级），供从表格类清单迁移时参考。
- **FR-002**: 导入 MUST 分为"校验预览"与"确认导入"两步；校验预览 MUST NOT 写入或修改任何数据，包括权限点、角色绑定，以及**任何审计记录**（成功与失败均不写）——预览是只读动作，管理员反复点击校验 MUST NOT 在审计日志中留下痕迹。
- **FR-003**: 校验预览 MUST 返回三态计数（将新增 / 将更新 / 无变化）；其中"将更新"的条目里 MUST 单独披露"上级将变更"的条数（见 FR-016），使改写层级这件事在写入前可见。确认导入 MUST 返回同口径的实际结果；对同一份输入，两者的计数 MUST 一致（并发改动除外）。
- **FR-004**: 确认导入 MUST 在单个事务内完成：任一条目校验或写入失败时 MUST 全部回滚，MUST NOT 留下部分写入的权限点。
- **FR-005**: 校验失败时 MUST 给出可定位的错误清单（第几条、结构路径、字段、原因），MUST 覆盖同一份输入中的多处问题（默认最多展示 20 条），MUST NOT 只报第一条。

**JSON 结构与层级**

- **FR-006**: 输入 MUST 为一个 JSON 对象，含 `permissions` 数组；MAY 含 `version`（当前仅支持 `1`，其它值 MUST 拒绝并说明支持的版本）与 `mode`（当前仅支持 `merge`；`replace` 等其它值 MUST 拒绝并说明"暂不支持全量对齐"）；`permissions` 的每个元素 MUST 含 `code` 与 `name`，MAY 含 `description`、`sort`、`children`（`children` 递归同构）。除上述字段外的未知字段 MUST 拒绝并指出字段名。
- **FR-007**: 层级 MUST 仅通过 `children` 嵌套表达；输入中 MUST NOT 出现内部标识（权限点 ID、父级 ID）作为引用。
- **FR-008**: 省略 `sort` 时 MUST 按同级数组中的出现顺序自动分配递增值，使 JSON 书写顺序即展示顺序。
- **FR-009**: 同一份输入内 `code` MUST 全局唯一（跨层级查重）；重复时 MUST 拒绝并同时指出两处及以上位置。
- **FR-010**: 导入 MUST 复用既有的编码规则与字段长度约束（编码允许字符与长度、名称与描述长度），MUST NOT 因批量导入而放宽校验。
- **FR-011**: 编码 MUST NOT 强制以父级编码为前缀；不符合前缀习惯时 MUST 仅给出提示，MUST NOT 阻断导入。
- **FR-012**: 层级深度 MUST 沿用既有单条创建的同一上限（100 层），MUST NOT 为导入设置更严格的上限（否则库里更深的树"能导出、导不回"，违背 FR-019 的闭环承诺）；超过时 MUST 在校验阶段拒绝并指出超限节点的路径与实际深度。
- **FR-013**: 单次导入 MUST 有数量上限（1000 条）与请求体积上限（512KB，需覆盖 1000 条填满编码/名称/描述的最坏体积）；超出时 MUST 拒绝并提示上限值。提示措辞 MUST 按超限类型区分：**条数超限**须含本次实际条数（便于裁剪）；**体积超限**时请求体无法完整解析，MUST NOT 声称知道条数，须给出实际上限并明确"可能是描述或名称过长所致"。该上限 MUST 只约束**单次提交**，MUST NOT 被实现或表述为"应用权限点总量上限"；应用内权限点总量沿用现状，MUST NOT 因本特性新增配额或把导入条数与既有总量相加后拒绝。

**写入语义**

- **FR-014**: 导入 MUST 以 `code` 作为幂等键：库中已存在且字段无变化者 MUST 计为"无变化"且 MUST NOT 产生写操作；字段有变化者 MUST 计为"更新"并更新对应字段。
- **FR-015**: 本版本（v1）MUST 只做"合并"（新增 + 更新）；MUST NOT 删除输入中未出现、但库内已存在的权限点。
- **FR-016**: 写入 MUST 保证父级先于子级落库（与数组顺序无关），且子级的父级 MUST 指向本次导入中对应的节点。当库内已存在的权限点在输入中的上级与现状不同时，MUST 按输入改写其上级（嵌套结构为完整树、每个节点只出现一次，故不会形成环）；该变更 MUST 计入"更新"，并在校验预览中按条数披露，且 MUST 额外给出**至多 20 条可核对的上级变更明细**（权限编码、原上级编码、新上级编码）——只给条数会让管理员在确认前无法分辨"改名"与"换爹"这两类风险完全不同的更新。
- **FR-017**: 导入 MUST NOT 修改任何角色与权限点的绑定关系，MUST NOT 修改成员关系，MUST NOT 改变权限点被引用时的既有约束。
- **FR-018**: 并发导入同一应用时 MUST NOT 产生重复权限点或半成品层级；因唯一性冲突失败的一方 MUST 得到"请刷新后重试"的可操作提示。

**导出**

- **FR-019**: 应用权限管理 MUST 提供"导出"能力，产出与导入完全同构的 JSON（含 `version: 1` 与 `mode: "merge"`、嵌套 `children`、不含内部标识、编码原样保留），使"导出 → 导入"到另一应用或另一环境成为闭环；导出文件被原样回导时 MUST NOT 因字段校验被拒绝。导出 MUST 覆盖该应用**全部**权限点，MUST NOT 复用带条数上限的列表查询而静默截断；当导出内容因**为空、条数、体积或深度**超出导入侧上限而无法回导时，MUST 在导出响应中显式给出"不可回导"的判定与原因，使管理员在下载前就知道这份文件只能用于备份。**该判定的体积口径 MUST 与下载文件的实际字节一致**（按格式化后的序列化结果计算，MUST NOT 用更小的紧凑序列化结果代替），否则判定会与实际回导结果不符。当导出条数超过列表页的展示上限时，提示中 MUST 说明列表页的展示条数，避免被误认为导出出错。

**两端一致与权限**

- **FR-020**: admin 端与门户应用管理员端 MUST 提供同一套导入、导出与校验能力；同一份输入在两端的校验结论与导入结果 MUST 一致。
- **FR-021**: admin 端 MUST 仅平台管理员可操作；门户 MUST 仅该应用的应用管理员可操作；拒绝语义 MUST 与既有应用管理端点统一，MUST NOT 泄露应用是否存在。
- **FR-022**: 应用不存在或被停用时导入 MUST 被拒绝，原因说明 MUST 与既有端点一致。

**审计**

- **FR-023**: 有实际写入的成功导入 MUST 写入 1 条聚合审计事件，内容 MUST 包含：应用、新增/更新/无变化条数、上级变更条数、来源（粘贴/文件）、操作者、结果与时间。为使误导入事后可处置，MUST 另记**本次新增权限点的标识**（超过 20 项时只记前 20 个与其总数，沿用既有"被解绑标识快照"的截断规则）与**导入文档的指纹**（哈希，不存原文），使"这次导入新增了哪些点、当时导入的是哪份文件"可验证。**新增与更新均为 0 的重复导入（全量无变化）MUST NOT 写入成功事件**——无数据变化的动作不应在审计页留下看似"又改了一次"的记录。
- **FR-024**: 导入 MUST NOT 为每条权限点逐条写入审计事件（1000 条输入不得产生 1000 条事件）。
- **FR-025**: "确认导入"因**业务拒绝**失败时（并发冲突、条数/体积超限、应用不存在或已停用）MUST 记录 1 条失败事件（含失败原因分类），MUST NOT 记为成功；因**内容非法**失败（`APP_PERMISSION_IMPORT_INVALID`）与鉴权失败 MUST NOT 记录——这类失败与校验预览同为"改内容再试"的无后果动作，逐次留痕会淹没审计页（与既有"输入格式错误不记"的口径一致）。"校验预览"无论成功或失败 MUST NOT 写入任何审计事件。
- **FR-026**: 新增的事件类型 MUST 登记进既有的事件注册表与一致性检查范围，保证"代码有、规范有、文档有"不漂移。

**校验职责与响应形态**

- **FR-027**: 输入 MUST NOT 被当作可信数据落库；所有字段 MUST 经服务端校验。前端校验仅为体验优化，MUST NOT 作为唯一防线。
- **FR-028**: 前端 MUST 只做"是否为空、是否为合法 JSON"的基础检查；编码规则、层级、重复、超量等语义结论 MUST 以服务端返回为准。
- **FR-029**: 确认导入失败时 MUST 返回可分类的稳定错误码：内容非法（结构、字段、编码规则、跨层重复、层级超深、字段超长）用 `APP_PERMISSION_IMPORT_INVALID`；条数或体积超限用 `APP_PERMISSION_IMPORT_TOO_LARGE`（提示需裁剪后重试）。两者 MUST 先登记进规范再使用。失败响应 MUST NOT 携带结构化明细（遵循既有统一响应约束，失败时 `data` 为 null）；可分位置的问题清单 MUST 由校验预览的成功响应提供。前端 MUST 引导用户先预览再导入，MUST NOT 依赖失败响应做逐条定位。

**边界与降级**

- **FR-030**: 校验或导入失败后 MUST 保留管理员已输入的内容（不清空编辑器），MUST NOT 自动重试。
- **FR-031**: 权限点字典规模 MUST NOT 影响用户令牌与用户信息中权限点的既有语义：字典本身可上千条，单个用户实际获得的权限点集合沿用既有绑定上限与既有计算方式。

### Key Entities *(include if feature involves data)*

- **权限点定义（字典项）**：应用内的一条权限声明，含编码（应用内唯一、区分大小写）、名称、描述、同级排序、所属父级。是角色授予的最小单位。
- **导入输入文档**：一份以嵌套 `children` 表达层级的权限点清单，含可选的版本与模式信息；不含任何内部标识，可跨应用、跨环境搬运。
- **导入结果（一次性产物，不持久化）**：三态计数（新增/更新/无变化）、问题清单（位置/字段/原因）、来源与操作者。
- **聚合审计事件**：一次导入对应一条记录，承载上述计数与来源，用于事后追责与复盘。
- **权限点树（派生视图）**：按父子关系组织的展示结构，由权限点定义派生，不单独存储。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 导入 500 条权限点时，管理员的人工操作次数 ≤ 3 次（粘贴或选文件 → 校验 → 确认），改前需要逐条新建 500 次。
- **SC-002**: 准备 20 份覆盖各类错误的样例输入（语法错误、缺字段、字段非法字符、超长、跨层重复、超深、超量、空数组），100% 能在校验阶段定位到具体位置与原因；0 例出现"提示通过但导入后层级/字段不对"。
- **SC-003**: 同一份输入连续提交两次，第二次的新增数与更新数均为 0、无变化数等于输入条数，且不产生新的成功审计事件。
- **SC-004**: 从应用 A 导出再导入到空权限的应用 B，权限点数量、编码集合与父子结构 100% 一致。
- **SC-005**: 1000 条、5 层嵌套的输入，校验预览的服务端 p95 ≤ 3 秒，确认导入的服务端 p95 ≤ 5 秒。
- **SC-006**: 任意一次失败导入后，权限点集合与导入前逐条一致（部分写入条数为 0）。
- **SC-007**: 同一份输入分别在 admin 端与门户端校验，结论一致率 100%（同时通过或给出同一组位置与原因）；导入后的三态计数一致。
- **SC-008**: 一次导入在审计日志中恰好产生 1 条记录（1000 条输入也不产生 1000 条），且其中包含可回答"谁、何时、为哪个应用、新增/更新多少条"的全部信息。

## Assumptions

- **只做合并（v1 不做全量对齐）**：导入语义为"新增 + 更新"，不删除 JSON 中未出现的既有权限点。原因是删除会连带解除角色绑定（现有删除逻辑即在同事务内解绑），批量删除的风险远高于收益；需要"全量对齐"的场景留待后续单独设计并配套影响面预览。
- **幂等键为编码**：以 `code` 识别同一权限点，而不是把内部标识写进 JSON。理由有二：编码本就是应用内唯一键；跨环境搬运时内部标识必然冲突，用它做键会让导出再导入直接失败。
- **层级只支持嵌套**：仅接受 `children` 嵌套，不接受扁平 `parentCode`，也不接受 `parentId`。混合多种表达会让"同一份文件两种写法"的语义不清，且嵌套最贴近管理员的心智模型。
- **不强制编码前缀**：不要求子权限点编码以父级编码开头。存量环境未必是路径式命名，若强制，则"导出再导入"会因历史数据而失败；前缀习惯通过校验提示引导。
- **校验分层**：结构性检查（字段存在性、类型、未知字段、数组形态）参照一份入库的 JSON Schema 契约执行；语义检查（编码规则、长度、跨层查重、深度、数量上限、与存量比对）由服务端业务校验完成——后者本质上无法用 JSON Schema 表达（需要给出业务化的原因与位置）。
- **不引入新的校验引擎依赖**：以"服务端为唯一判定方 + 前端只做语法检查"实现；JSON Schema 文件作为契约文档与样例来源，两端一致性由一组共享样例输入锁住，避免为批量校验引入一个仅用于此处的运行时依赖。
- **视图层零新增依赖**：导入/导出界面复用既有组件库与既有权限树的展示组件，不引入代码编辑器类重依赖。
- **失败响应不带结构化明细**：遵循项目既有"失败响应 `data` 必须为 null"的统一响应约束，结构化问题清单只出现在校验预览的成功响应中；正常流程要求前端先预览再导入，因此不牺牲可用性。
- **审计只记聚合**：一次有实际写入的导入一条事件；无数据变化的重复导入不记。逐条记录会在一秒内写入上千行，既冲高审计写入量，也让审计页按类型筛选失去意义。
- **层级上限与单条创建对齐（100 层）**：不另设"导入专用"的浅层上限。独立上限会让库里更深的树"能导出、导不回"，与 FR-019 的闭环承诺冲突；而"权限字典应该只有三层"是命名习惯问题，应由校验提示引导，不应做成硬限制。
- **导出可回导性显式判定**：导入侧的上限（1000 条 / 512KB / 100 层）同样作用于"回导"，但导出本身不做限制（备份与人工参考是正当用途）。因此导出响应必须携带可回导判定与原因，让管理员在下载前就知道这份文件能不能搬走；判定的体积口径必须与下载文件的实际字节一致，空文档也判为不可回导。
- **不新增"导入批次"实体**：出于同样的"不预留结构"考虑，v1 不建批次表、不做撤销导入；代价是"误导入"无法一键回滚，因此用审计里的新增标识快照（前 20 + 总数）与文档哈希提供最小可处置线索。若将来确实需要批量回滚，再按需引入批次实体（该决策已被显式记录，避免实现期临时加表）。
- **两端同时开放**：v1 起 admin 端与门户应用管理员端同时提供该能力（与成员、角色、权限点单条维护的既有口径一致），不做"先 admin 灰度"。
- **不改变令牌语义**：权限点字典规模与实际下发的权限点集合无关；后者仍由角色绑定关系决定，沿用既有绑定上限，不因本特性调整。
